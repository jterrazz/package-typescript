# Architecture

What is inside the one devDependency, for whoever changes it. A project using the toolchain needs none of this page: [Getting started](../start/getting-started.md) is its door.

The package is two sides that never mix. `lint/` JUDGES: every rule, every pass, every verdict a project can receive. `src/` RUNS: the command that orchestrates the tools, the config presets a project's own files extend, and the entries a project imports. Both are TypeScript, built into `dist/`, which is what ships.

| Layer           | Holds                                                                                                                                              | Reached by                                                                                                                                               |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lint/`         | every judgement: the declarations a project is held to, and the kit that runs them                                                                 | `src/`, and a consumer through `./oxlint`, `./config`, `./rules` and `./docs`                                                                            |
| `src/commands/` | the command: one folder per subcommand a user types, its `<name>.command.ts` and what only it uses; `check/` with its `passes/` and `report/`      | the bin, and the spec harness's selecting launcher ([Test](https://github.com/jterrazz/package-typescript/blob/main/docs/guides/test.md#the-self-rules)) |
| `src/drivers/`  | one folder per external tool, the only code that spawns it, resolves its binary or imports its package; `run.ts`, the one process runner           | `src/commands/`                                                                                                                                          |
| `src/presets/`  | the tsconfig presets, the formatting, and the knip preset the command derives a config from                                                        | a consumer's `tsconfig.json` by `extends`, the command by path                                                                                           |
| `src/standard/` | the standard, data only: `standard.ts`, `kinds/<kind>.ts`, `platforms/<platform>.ts` ([Configuration](../reference/configuration.md#the-standard)) | `lint/consumer/catalogue/preset.ts`, which merges it for a project's declaration                                                                         |
| `src/`          | the entries: `./oxfmt`, the `#command` private import, and `typescript.bin.ts`, the bin that hands the command line to the command                 | a consumer's `oxfmt.config.ts`, the specs, and the `typescript` binary                                                                                   |

The `typescript` bin is built with the rest: a registry install links the command from `dist/typescript.js`. `dist/` is the build's product, ignored by git and published ([Building this package](#building-this-package)). The API is the types the build emits, and no reference is generated from them: the declarations a project's editor resolves are the one copy.

## The judging layer

`lint/` has one tree in every repository of the estate, and the Names pass holds every consumer to it ([Quality checks](../reference/quality-checks.md#the-lint-tree)). It is split by audience first. Only entries sit at its root: each `index[.<name>].ts`, named by [the entry grammar](../reference/quality-checks.md#the-entry-grammar), is a subpath the package publishes or a private `#` import it builds. Each folder below is one of three.

### The consumer catalogue

- `preset.ts`: the toolchain's own preset, the package's standard, `src/standard/`, merged for a project's kind and platform ([Configuration § The standard](../reference/configuration.md#the-standard)).
- `manifest.json`: the consumer rows of the manifest.
- `findings.json`: every id a pass or a rule prints, with its family and the one sentence it holds a project to, rendered into the id tables of [Quality checks](../reference/quality-checks.md).
- `families.json`: the closed list of those families.

A refusal of the run rather than of the project (`baseline-ratchet`, `baseline-unreadable`, `oxlint-config-unparsed`, `oxlint-config-commonjs`) belongs to no family, prints a bare id and is in none of them.

### The checker

`kit/checker/` is the one runner and command line of the node passes:

- `checker.ts` reads the command line, runs the pass it is handed over what the kit reads and the settings resolved through the presets the module at the root of `lint/` hands it, prints and reports its findings, judges a held pass against the baseline and writes a fix;
- `report-line.ts` writes a positioned finding in the compiler's convention, and `stop.ts` unwinds a run to its exit code;
- `baseline.ts` is the `baseline` command, which refuses an oxlint rule left in the section or writes the section from the Architecture and Names counts;
- `project-queries.ts` holds what the command asks of a project.

### The laws that keep it apart

Two laws keep the audiences apart. **Declarations only:** `consumer/` and `self/` hold a rule, a check, a decision on an upstream rule, a catalogue entry, or their tests. A module there runs as no program and hands another module no function but one named for its file, and code the declarations share is `kit/`'s; the Names pass refuses the rest ([Quality checks](../reference/quality-checks.md#the-lint-tree)). **The kit knows no declaration:** it is handed the profile table, the rows, the fragments, the passes and the plugin paths, and a module at the root of `lint/` composes them.

An import in `lint/` goes one way, the same in every repository that keeps the tree:

- `kit/` imports nothing of `consumer/`, `self/` or `src/`;
- `consumer/catalogue/` imports only `kit/` and `src/standard/`, since it is data at the bottom: here the toolchain's preset, `preset.ts`, composed from the standard, beside JSON rows the self corpus holds each printed id and sentence to and renders into the reference pages;
- `consumer/rulebook/`, `consumer/rules/` and `consumer/checks/` import the catalogue and `kit/`, never each other, and an entry imports any of them;
- inside `self/` the arrow is the same: `self/catalogue/` imports only `kit/` and the consumer catalogue it extends; `self/rules/`, `self/checks/` and `self/corpus/` their catalogue, `consumer/` and `kit/`, never each other.

A catalogue's own tests are test material, and read the declarations they audit. Nothing shipped imports `self/`, and `src/` reaches no declaration of `consumer/` or `self/`, only `kit/` and the modules at the root of `lint/`. The standard declares each arrow as a law of its own, so every repository that keeps a `lint/` tree is held to it with no line of its own, and the Architecture pass holds the resolved import graph to it ([Configuration](../reference/configuration.md#the-standard)).

`lint/` and `src/` import each other one way only, and a module both need has one owner: the side whose behaviour it defines. Here `src/` is the command that runs `lint/`, so `src/` imports `lint/` through the modules at its root and `kit/` alone, never `self/`. `self/`, never shipped, may read `src/`: it judges the repository's own product. The shipped `lint/` never reads `src/` but `src/standard/` (the data both apply, of which `src/` holds no code), though its tests, which are not shipped, may run a rule through the package that ships it. The same law holds in `@jterrazz/test`.

### The rulebook

The rulebook is a manifest, not a config: one fragment per plugin, stating a decision per rule, and this package's own suite refusing a fragment that breaks either invariant. A level is `error` or `off`, and an `off` carries one of five recorded reasons ([Test](https://github.com/jterrazz/package-typescript/blob/main/docs/guides/test.md#who-a-rule-is-for)).

Three steps and nothing between them:

1. `lint/consumer/rulebook/profiles.ts` says which fragments each profile carries;
2. `lint/kit/compiler/compile.ts` turns a fragment into the plain oxlint config object oxlint itself reads, and merges those objects;
3. `lint/index.rulebook.ts` compiles the table, and derives a project's config from it: the profile of the declared platform, each preset's rules, the project's own `typescript.oxlint`, and, in a workspace, each member's own scoped to its folder.

`lint/index.oxlint.ts` is that derivation for a module's directory, `oxlintConfig(import.meta.url)`: every project's `oxlint.config.ts` calls it with its own `import.meta.url`. Where that file is missing, `check` hands oxlint the private `#oxlint-standin` entry by path, the same call on the project root the command runs in; `#oxfmt-standin` is oxfmt's. A settings file the derivation cannot read throws its four-part refusal, so oxlint and the editor print the lesson rather than lint with a config nobody declared. The rule decisions are [Lint presets](../reference/lint-presets.md)'s, catalogued there from the same manifest.

## Building this package

The package is TypeScript, and what ships is its build: `npm run build` derives the build from the manifest, as `typescript build` does for every consumer ([Building](../reference/building.md)), into `dist/`, which git ignores and `files` publishes, with the JSON presets beside it as data, served where they are written. Every entry of the exports map and of the `imports` map (the command, the checker program, the rulebook, the oxlint plugin) is an entry of the build; each carries the declaration the build generates from its source, so a type has one owner.

A build step is a precondition like an install: `make build` precedes `make lint` and `make test`, and the specs drive the built command. The toolchain builds itself with the build plan it ships to everyone else: tsdown first compiles `src/commands/build/self-build.ts` alone into `.artifacts/bootstrap/`, which then runs the plan over the manifest. There is no second toolchain, only the order of two gestures.

The plan reads `jterrazz.config.ts`, and that file imports the package by its own name: `@jterrazz/typescript/config` itself, and `@jterrazz/typescript/rules` through `@jterrazz/test/config`. A clone holds no build of either, so before it reads the settings the bootstrap resolves the package's own name to the sources its exports map is built from, and a source's `.js` import to the `.ts` beside it (`src/commands/build/own-sources.ts`). The settings are thus read through the presets the checkout holds, never through a `dist/` an earlier build left. `specs/cli/build/fresh-clone.spec.ts` builds a copy of the tree that holds no build at all, as CI's checkout does.

## The command

`typescript check` runs up to fifteen passes, most of them separate processes: tsc, oxlint, oxfmt, knip, publint, dependency-cruiser and the checker program of this package's own. The command starts them all, awaits each, and reports each in one fixed order ([Quality checks](../reference/quality-checks.md)). A pass whose answer is this package's own code (the knip config merged, the sweep a tool is handed) runs in the command itself, as a function; a tool's own output, oxlint's included, is printed as the tool printed it.

The rule the split follows: **the command decides whether a gate applies; the checker decides what the gate says.** Whether a `.gitignore` exists, whether a repository is a repository, which workspace members own a `specs/`: those are the command's probes. What is wrong with a `.gitignore`, or with a `docs/` tree, is a pass's, because the answer needs parsing and a rule roster.

A refusal the command's own code can meet from a project (a map it cannot compile, a tree its sweep cannot read) is thrown in four parts, `found: ... · why: ... · fix: ... · read: ...`, the read a heading of this manual; one only the toolchain can cause is `invariant()`, whose message says the bug is the toolchain's ([Test](https://github.com/jterrazz/package-typescript/blob/main/docs/guides/test.md#who-a-rule-is-for)).

### Commands and drivers

`src/commands/main.ts` dispatches the command line, after `arguments.ts` has read it against the subcommand's surface in `surface.ts` (the flags it declares, its help, the page that owns it), so a help request or a refused line never reaches the subcommand ([Commands § Flags and help](../reference/commands.md#flags-and-help)). It imports a subcommand only when it dispatches to it, one `import()` per entry of its table, so a process that runs `clean` loads none of `check`'s modules, and a mutant of one subcommand is credited to the specs that spawn that one ([ADR-030](../decisions/030-the-suite-stage-pays-for-what-its-change-reaches-on-every-worker.md)). Each subcommand a user types (`build`, `check`, `fix`, `mutation`, `baseline`, `doctor` and the rest) is one folder, `src/commands/<name>/`, entered by `<name>.command.ts`, and what only that subcommand uses sits in its folder. `check/` is the widest: `check.command.ts` and `fix/fix.command.ts` share its run, `passes/` starts each pass and decides whether it applies, `report/` settles the verdicts and prints them. A module two subcommands share lives with the one it serves, or in `lint/kit/` when it reads a project.

The tools run beneath them, each from one folder: `src/drivers/<tool>/<tool>.ts` resolves the tool's binary, spawns it and imports its package. The tools are `oxlint`, `oxfmt`, `tsc`, `tsdown`, `knip`, `stryker`, `prettier`, `astro`, `node`, and `checker`, this package's own checker program, which runs as a process like the rest. In the command's process a tool is spawned under `src/drivers/` alone, most through `run.ts`, the runner the drivers share; a command calls a driver, a driver calls no command and no other tool's driver, and what two drivers share sits at the root of `src/drivers/`. A tool's config, where it has one, is its folder of `src/presets/`. The folder is `drivers/` and not `tools/`, since `tools` is a word of the grab-bag roster the Names pass refuses ([Quality checks](../reference/quality-checks.md#the-names-tree-pass)); the owner confirmed the name on 2026-10-15, one tool to one folder, and `tools` stays on the roster.

The checker program is a process of its own, and the shipped `lint/` never reads `src/`, so the tools its passes hand the tree to (`dependency-cruiser`, `ls-lint`, `rumdl`, `publint`, `attw`, oxlint's `--print-config` and `gitleaks`) run through its one runner, `lint/kit/checker/tool-run.ts`. Their drivers resolve the binary and the command hands it to the pass by flag; gitleaks, which no dependency of this package ships, is the one on the machine's PATH, probed before it runs. Git is no tool the command drives but how the kit reads a project (what it tracks, what it ignores, what changed), and `lint/kit/project/git.ts` is its one runner, which the kit's readers and the `mutation` command share.

This repository's own suite holds the tree to both. Each of these fails it at its module: a subcommand with no folder, a folder with no command file, a process spawned in `src/` outside `src/drivers/` (directly or through the checker's runner) or a binary resolved there, a tool's package imported or resolved outside its driver and its preset, and a driver reaching another driver or a command ([Test § The self rules](https://github.com/jterrazz/package-typescript/blob/main/docs/guides/test.md#the-self-rules)).

Five subpaths, all declared in the exports map, each a built `.js` beside the `.d.ts` the build generates, and the tsconfig presets as data:

| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@jterrazz/typescript/oxlint`     | `oxlintConfig(url)`, which takes the config file's `import.meta.url` and derives the oxlint config from the `jterrazz.config.ts` beside it ([Quality checks § The derived files](../reference/quality-checks.md#the-derived-files)), and oxlint's config types |
| `@jterrazz/typescript/oxfmt`      | `oxfmtConfig(url)`, which derives the oxfmt config the same way, from the `jterrazz.config.ts` beside the file whose `import.meta.url` it is handed, and oxfmt's config types                                                                                  |
| `@jterrazz/typescript/config`     | `defineConfig()`, `definePreset()`, `JterrazzConfig`, `ProjectConfig`, `ProjectDeclaration`, `ProjectKind`, `Platform`, `TypescriptSettings`, `Preset` and the rest: the family's settings file, typed                                                         |
| `@jterrazz/typescript/docs`       | `auditDocs()` (the manual's rules, pure), `DocsRule` and `DOCS_RULES`, their ids, and `HEAD_LINES`, how many opening lines of a file they read                                                                                                                 |
| `@jterrazz/typescript/rules`      | the kit a package writes its rules with: the lesson, the rule and the check, the chapter projection, the baseline and its judges, the readers of a project ([Rules kit](../reference/rules-kit.md))                                                            |
| `@jterrazz/typescript/tsconfig/*` | the five tsconfig presets, `node`, `next`, `astro`, `expo` and `react`; `bun` takes `node`'s                                                                                                                                                                   |

The two editor entries are what a project's derived `oxlint.config.ts` and `oxfmt.config.ts` call, and nothing else: `oxlintConfig` and `oxfmtConfig` read the `jterrazz.config.ts` beside the module whose `import.meta.url` they are handed, the config file itself, so the tool's working directory never decides the config ([Quality checks § The derived files](../reference/quality-checks.md#the-derived-files)). A layer map is not a lint fragment: it is declared in `jterrazz.config.ts` and judged by dependency-cruiser ([Quality checks](../reference/quality-checks.md#the-architecture-layer-map-pass)). Each config TYPE (`OxlintConfig`, `OxfmtConfig`) is re-exported from the tool that owns it, never restated here: a hand copy drifts. What the package runs but no consumer imports (the command, the checker program, the rulebook, the plugin) is a private `#` import of its own manifest, reachable from inside the package alone. The specs under `specs/cli/node/` and `specs/cli/tsc/` install the packed tarball into a consumer's project, load every subpath by its public specifier under each condition, and compile a consumer module against the published declarations: the package is its own consumer #1.

`./config` types the one settings file of the whole family, `jterrazz.config.ts`, and the presets it lists ([Configuration](../reference/configuration.md#presets)). `JterrazzConfig` is an interface so that each sibling package adds its own section by merging into it (`@jterrazz/test` declares `test`), and this entry never names a section it does not read.

`./rules` is the kit of `lint/`, exported: what a sibling package needs to write a rule, a check, its chapter and its debt the way this package does, so the family keeps one copy of each ([ADR-016](../decisions/016-one-engine-writes-every-rule.md)).

`OXLINT_CONFIG_NAMES`, on `./rules`, is the one list of the names an oxlint config may take. `check` and `fix` read it to decide whether a project has its derived file or is handed the entry by path, and `@jterrazz/test`'s checker reads it from the kit rather than from a copy, so it counts a config exactly where this toolchain does. It has no subpath of its own: a subpath only a sibling package reads is a line of the kit that sibling already imports.

`./docs` is the odd one out: it is not a config, it is a gate's rules, exported because that gate has two readers. `typescript check` reads a project it is installed in; an estate sweep reads clones it has installed nothing into. One pure function over a plain tree, and the rule ids, sentences and rosters stay in one executable copy. Its second reader is the estate's own CLI, not a sibling package, which is why it keeps a subpath of its own rather than a line of `./rules`.

## Two TypeScript compilers, on purpose

`typescript check` type-checks with the official TypeScript 7 Go compiler, pulled in through the per-platform `@typescript/typescript-*` optionalDependencies and resolved by path by the command.

The ordinary `typescript` dependency stays on ^6 because two consumers need the JavaScript compiler API that the Go package no longer ships: `dependency-cruiser` (a `typescript <7` peer) and `eslint-plugin-perfectionist`, which does a bare `require('typescript')`.

**Never add `typescript@7`, or an npm alias of it, to this tree.** Under pnpm's hoist fallback it can hijack perfectionist's lookup and fail intermittently with `isExternalModuleNameRelative is not a function`.

## The unit is the workspace package

Every per-package gate measures from the nearest `package.json`, never from the repository: a workspace root runs those gates once per member, and a single-package project is the one run it always was. `lint/kit/project/workspace-members.ts` answers whether the root is a monorepo (`isMonorepoRoot`, read from the `workspaces` npm owns, never from a declared kind) and what its members are, and every caller asks it rather than guessing.

The one gate that measures from the repository instead is the manual's, because a manual answers for a whole tree ([Quality checks](../reference/quality-checks.md)).
