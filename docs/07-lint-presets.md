# Lint presets

Every rule of every plugin this package loads is decided by name, at `error` or at `off` with a recorded reason — that manifest is `rules/`, and a profile is a pre-composed, tested slice of it that a consumer names in one line.

```ts
// oxlint.config.ts
import { defineConfig, node } from '@jterrazz/typescript/oxlint';

export default defineConfig(node);
```

## The four laws

1. **Every rule is decided, by name.** `categories` appears in no config this package ships. A category switch arms rules of plugins the config never names — inert until a framework config activates the plugin, then firing unannounced — so `oxlint --rules` is the roster and every non-nursery rule of a loaded plugin is present as `on` or `off`. Nursery is off wholesale; upstream calls it unstable.
2. **Default is ON, at `error`, with the strictest sensible options.** There is no `warn` tier. An `off` needs exactly one of five recorded reasons, and "too strict" is not among them.
3. **One rulebook, every profile.** A profile adds a framework's plugins and its ignore patterns. It never relaxes core.
4. **Sorting is formatting.** oxfmt owns import order, `package.json` key order and Tailwind class order. perfectionist keeps only what oxfmt does not sort.

### The five reasons an `off` may carry

| Kind         | What it claims                                                      | Proved by                                  |
| ------------ | ------------------------------------------------------------------- | ------------------------------------------ |
| `formatter`  | It fights oxfmt — the two rewrite the same bytes                    | `specs/cli/preset/fixpoint.test.ts`        |
| `exclusive`  | It cannot hold beside a rule that is on, which it names             | `specs/cli/preset/exclusive-pairs.test.ts` |
| `convention` | It refuses a convention the estate holds, whose page it names       | the page                                   |
| `evidence`   | A measured false-positive rate on real estate code, cited           | the measurement                            |
| `covered`    | TypeScript, or a stronger rule that is on, already names the defect | the named rule                             |

`rules/_contract.js` refuses a fragment that breaks either invariant at load time, so a rulebook with an unreasoned `off` cannot be imported at all.

## The profiles

| Profile   | Adds to the rulebook                                                  | tsconfig preset    |
| --------- | --------------------------------------------------------------------- | ------------------ |
| `node`    | nothing — services and command-line tools                             | `tsconfig/node`    |
| `library` | the committed `docs/reference/` tree is not linted                    | `tsconfig/library` |
| `next`    | react, jsx-a11y, nextjs; `import/extensions` at `never`               | `tsconfig/next`    |
| `astro`   | react, jsx-a11y, the `*.astro` decisions; Next is a restricted import | `tsconfig/astro`   |
| `expo`    | react, jsx-a11y, the React Native platform decisions                  | `tsconfig/expo`    |
| `bun`     | the globals Bun's runtime defines                                     | `tsconfig/node`    |
| `react`   | react, jsx-a11y; `import/extensions` at `never`, no framework plugin  | `tsconfig/react`   |

Type-aware linting is on in every one of them (`options.typeAware`), answered by `oxlint-tsgolint`, which embeds its own TypeScript — a consumer gets the 59 type-aware rules without migrating to TypeScript 7.

Two conditions make those rules real, and both fail silently when they are not met. `oxlint --type-aware` finds tsgolint by walking up for `node_modules/.bin/tsgolint`; and a file outside the TypeScript program has no parameter types, so every value in it is `any`. That second one is why the `no-unsafe-*` family and `strict-boolean-expressions` are off inside `**/*.js`: there they report the language, not a defect. A tree with JavaScript sources includes it in its `tsconfig.json`.

### `import/extensions` — the one rule two platforms answer differently

Node ESM resolves a specifier literally and needs the `.js`; a bundler resolves it and refuses one. `node`, `library` and `bun` carry `always`; `next`, `astro`, `expo` and `react` carry `never`. Asset specifiers keep their extension everywhere, because a bundler resolves them BY it, and `astro` keeps `.astro` for the same reason: Astro's `resolve.extensions` does not carry it, so a layout imported without it fails the build. Both are `error` — a profile changes the convention, never the level.

## `compose()` semantics

`compose(...configs)` merges deterministically, left to right:

| Keys                                                | Merge                                   |
| --------------------------------------------------- | --------------------------------------- |
| `extends`, `ignorePatterns`, `jsPlugins`, `plugins` | concatenated, duplicates dropped        |
| `overrides`                                         | concatenated, order kept, never deduped |
| `env`, `globals`, `options`, `rules`, `settings`    | shallow-merged, last wins per key       |
| anything else                                       | taken from the last config that sets it |

A project using `@jterrazz/test` composes its testing fragment explicitly — nothing is auto-detected:

```ts
import { testing } from '@jterrazz/test/oxlint';
import { compose, defineConfig, node } from '@jterrazz/typescript/oxlint';

export default defineConfig(compose(node, testing));
```

## The layer map

Architecture boundaries are a declared map, not a filename regex. `layers({ map })` compiles it to one `no-restricted-imports` override per layer, and `hexagonal` is the map this package ships:

```ts
import { compose, defineConfig, hexagonal, node } from '@jterrazz/typescript/oxlint';

export default defineConfig(compose(node, hexagonal));
```

- `domain/` imports no other layer.
- `application/use-cases/` and `application/ports/` reach the domain and the ports, never an implementation.
- `infrastructure/inbound/` reaches an outbound adapter through injection, not by import.
- `presentation/ui/atoms/` and `molecules/` stay clear of navigation.
- `presentation/features/` is independent, except for `features/common/`.

Three properties of oxlint shape the generated config, all three permanent:

- An override's rule **options REPLACE** the base entry; they never merge. So each layer's override carries that layer's COMPLETE pattern list, and nothing about layering is left in the base config.
- The `regex` matcher is **Rust regex, which has no lookahead**. "features may not import features, except common" is two globs: the deny glob, then the same glob negated with `!`.
- `no-restricted-imports` matches the **specifier string**, never a resolved path. `../beta/thing.js` does not carry the layer name and passes. A map is a textual boundary; a graph boundary is dependency-cruiser's.

A layer that declares `allowTypeImports: true` lets a type-only import cross its boundary: a type is a contract, not a runtime dependency, and a port may name the adapter's shape without loading it.

A map whose layers share a `files` glob is refused at build time rather than shipped: with replace semantics, the second override would silently erase the first.

### `import/no-cycle`

On in core, and worth knowing what it does not see: oxlint's implementation ignores type-only imports, so a value import one way and an `import type` back is invisible to it (oxc#20551).

## Fixers that lie

A fixer that changes MEANING is never applied unattended. The rules below stay armed — `check` reports them and a human answers them — and `fix` runs with each one allowed, so the rewrite never lands. Each is marked in the manifest with what its rewrite does, and this list is that mark's projection.

### Module augmentation

The first entry of that list is the one a scope also answers. An augmentation merges into an existing declaration only as an INTERFACE — a `type` alias redeclares the name, and every member of the original is lost — and the `export {}` beside it is what makes a file carrying `declare module` an augmentation rather than an ambient redeclaration. So `typescript/consistent-type-definitions` is OFF in `**/*.d.ts`, where augmentation is what a file is for, and on everywhere else, where the block is one part of a source file and a human answers the report with a suppression inside it. `typescript/no-useless-empty-export` stays on: it fires only where the file is already a module by another export, which is the case the `export {}` adds nothing to.

## The formatting decisions

100-char print width, 4-space indentation, single quotes, trailing commas everywhere, semicolons, LF. Those four do not move: twenty-eight repositories are written that way and two of them hold signed attestation bytes a reflow would invalidate.

The three sorters are law 4:

- **`sortImports`** — builtins and externals together, then internals, then the relative block, then styles; a blank line between groups, case-insensitive ascending inside one. It reorders import STATEMENTS and leaves the named specifiers inside one statement alone, which is why `perfectionist/sort-named-imports` stays on.
- **`sortPackageJson`** — on, scripts left in the order their author put them.
- **`sortTailwindcss`** — `class`, `className`, and the class-holding helpers (`clsx`, `cn`, `cva`, `tv`, `twMerge`, `twJoin`, `tw`).

perfectionist therefore keeps six rules, all of them about an order oxfmt does not touch: union types, intersection types, JSX props, heritage clauses, named imports, named exports.

## Estate conventions the rulebook rests on

Several `off` reasons of kind `convention` name this page. Here is what they name:

- **An object orders by meaning**, not alphabetically — and generic inference is order-sensitive, so a sorted object is not the same program (`sort-keys`).
- **An export sits with the declaration it exports** (`import/exports-last`, `import/group-exports`).
- **A module exports what it owns by name**; a config file is a default export (`import/no-named-export`, `import/prefer-default-export`, `import/no-default-export`).
- **A relative parent import** is how a package reaches its own sibling module; a layer boundary is the map's job, not the path shape's (`import/no-relative-parent-imports`).
- **`null` is what the platform and JSON APIs return**; a codebase that refuses it grows a translation layer at every boundary (`unicorn/no-null`).
- **A one-shot CLI script has no event loop to protect** (`node/no-sync`), and configuration arrives from the environment at the edge (`node/no-process-env`).
- **The estate compiles to ESNext on Node 24**, where optional chaining and object spread are native syntax (`oxc/no-optional-chaining`, `oxc/no-rest-spread-properties`).
- **A spec states its assertions, not their count**, and `vitest.config.ts` owns the timeout once (`vitest/prefer-expect-assertions`, `vitest/require-test-timeout`).
- **A vitest file is `*.test.ts` or `*.spec.ts`, or lives under `specs/` or `__tests__/`; a file another runner owns takes that runner's suffix.** The vitest rules read every file the first three name as one of theirs, and a spec that shared the suffix would be handed vitest's `expect` in place of its runner's. A Playwright file is `*.e2e.ts`; a jest-expo render test is `*.render.tsx`. Both are outside every vitest glob by construction, so nothing has to be ignored, and both stay in the type program.
- **A forgotten `await` in a spec is a defect, not a style.** `typescript/await-thenable`, `typescript/no-floating-promises` and `typescript/no-misused-promises` sit in the base rulebook and no override relaxes them, so every vitest glob inherits all three through tsgolint. It is what Playwright recommends on a spec tree, and for the same reason: an async matcher returns a promise, and a spec that drops it passes by asserting nothing.

## Unused code (knip)

`typescript check` runs [Knip](https://knip.dev/) with a base config auto-merged with any project-local `knip.json`:

- `@jterrazz/*` packages auto-ignored.
- Published libraries: `exports` / `types` / `files` rules auto-disabled.
- Convention paths (`_fixtures/`, `_expected/`, `docs/`) auto-ignored — at the root and inside every workspace member, because the convention belongs to the package. The two underscored names are `@jterrazz/test` 14's: what a spec stands on carries a leading underscore, and the bare `fixtures/` and `expected/` of earlier versions are no longer recognised.
- Plugin dependencies (`*-plugin-*`, `@scope/*`) auto-ignored.
- The toolchain's own config files — `oxlint.config.ts`, `oxfmt.config.ts`, `vitest.config.*`, `tsdown.config.*` — are named as `entry`, so they read as used even though a consumer never declares oxlint, oxfmt, vitest or tsdown itself: knip's own plugins for those tools only auto-enable when the tool is a DIRECT dependency, and this preset's contract is one devDependency ([Developing](02-developing.md)).

Create a `knip.json` only for project-specific overrides. It is read as **JSONC** — comments and trailing commas — so every override states why it exists ([Quality checks](06-quality-checks.md)):

```json
{
    "ignoreDependencies": [
        // Loaded by the bundler at runtime, never imported from source.
        "some-runtime-plugin"
    ]
}
```

`knip.jsonc` is read the same way, for a project that prefers the extension. The two differ only under the formatter: it drops a trailing comma from a `.json` and keeps one in a `.jsonc`, and the parser accepts either.

### Workspaces

Knip is workspace-aware on its own: it reads the `workspaces` globs from your `package.json` and reports per member from a single run — which is why `check` invokes it once, at the root. Per-member settings go under a `workspaces` key in your `knip.json`:

```json
{
    "workspaces": {
        "apps/api": { "ignoreDependencies": ["some-local-dep"] }
    }
}
```

The base preset declares no `workspaces`, so the key reaches knip exactly as written.
