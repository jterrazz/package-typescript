# Lint presets

The rulebook: what the Oxlint pass holds a project to. Every rule of every plugin this package loads is decided by name, either on at `error` or `off` with a recorded reason. A profile is a tested slice of that rulebook for one platform, which the project's declared `platform` picks in `jterrazz.config.ts` ([Getting started](../start/getting-started.md#1-declare-what-the-project-is)). The page opens on the laws every decision follows, then the profiles, then the decisions worth explaining, and ends on the full catalogue, generated from the rulebook itself.

## The four laws

1. **Every rule is decided, by name.** `categories` appears in no config this package ships. A category switch arms rules of plugins the config never names — inert until a framework config activates the plugin, then firing unannounced — so `oxlint --rules` is the roster and every non-nursery rule of a loaded plugin is present as `on` or `off`. Nursery is left undecided, since upstream calls it unstable — save a type-aware rule: every rule tsgolint runs is decided by name, nursery included, so a tsgolint release never adds a check no profile names.
2. **Default is ON, at `error`, with the strictest sensible options.** There is no `warn` tier. An `off` needs exactly one of five recorded reasons, and "too strict" is not among them.
3. **One rulebook, every profile.** A profile adds a framework's plugins and its ignore patterns. It never relaxes core.
4. **Sorting is formatting.** oxfmt owns import order, `package.json` key order and Tailwind class order. perfectionist keeps only what oxfmt does not sort.

### The five reasons an `off` may carry

| Kind         | What it claims                                                      | Proved by                            |
| ------------ | ------------------------------------------------------------------- | ------------------------------------ |
| `formatter`  | It fights oxfmt — the two rewrite the same bytes                    | this package's fixpoint suite        |
| `exclusive`  | It cannot hold beside a rule that is on, which it names             | this package's exclusive-pairs suite |
| `convention` | It refuses a convention the estate holds, whose page it names       | the page                             |
| `evidence`   | A measured false-positive rate on real estate code, cited           | the measurement                      |
| `covered`    | TypeScript, or a stronger rule that is on, already names the defect | the named rule                       |

This package's own suite refuses a fragment that breaks either invariant, so no profile ships an unreasoned `off`; that suite, and the two above, are [Test](https://github.com/jterrazz/package-typescript/blob/main/docs/guides/test.md#the-rulebook-has-seven-suites)'s.

### One owner per pair

## The profiles

| Profile   | Adds to the rulebook                                                                                                       | tsconfig preset    |
| --------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `node`    | nothing — services, command-line tools and published packages                                                              | `tsconfig/node`    |
| `next`    | react, jsx-a11y, nextjs; `import/extensions` at `never`                                                                    | `tsconfig/next`    |
| `astro`   | react, jsx-a11y, the `*.astro` decisions; Next is a restricted import                                                      | `tsconfig/astro`   |
| `expo`    | react, jsx-a11y, the React Native platform decisions                                                                       | `tsconfig/expo`    |
| `bun`     | the globals Bun's runtime defines                                                                                          | `tsconfig/node`    |
| `react`   | react, jsx-a11y; `import/extensions` at `never`, no framework plugin                                                       | `tsconfig/react`   |
| `browser` | the browser's globals, no Node's; `import/extensions` at `never`, no framework — plain DOM, an extension's popup or worker | `tsconfig/browser` |

The React profiles carry the React Compiler's rules — `react/refs`, `react/preserve-manual-memoization`, `react/set-state-in-effect`, `react/static-components`, `react/use-memo` and the rest of the `react/` rules that read a component as the compiler does — whether or not the app runs the compiler. They are kept on without it on evidence: in signews-mobile, which does not run it, they found a quiz sheet re-seeded on every render, an animation nobody rendered and three effects copying derived state, all real bugs. What they cannot give an app without the compiler is the memoisation they assume: the `react-perf` rules are off as covered by them, so an app that does not compile writes `useMemo` and `useCallback` where a profile says a value is rebuilt, and `react/jsx-no-constructed-context-values` still asks a provider's value to be stable.

Type-aware linting is on in every one of them (`options.typeAware`), answered by `oxlint-tsgolint`, which embeds its own TypeScript — a consumer gets the 59 type-aware rules, each decided by name, without migrating to TypeScript 7.

Two conditions make those rules real, and both fail silently when they are not met. `oxlint --type-aware` finds tsgolint by walking up for `node_modules/.bin/tsgolint`; and a file outside the TypeScript program has no parameter types, so every value in it is `any`. That second one is why the `no-unsafe-*` family and `strict-boolean-expressions` are off inside `**/*.js`: there they report the language, not a defect. A tree with JavaScript sources includes it in its `tsconfig.json`.

### `import/extensions` — the one rule two platforms answer differently

Node ESM resolves a specifier literally and needs the `.js`; a bundler resolves it and refuses one. `node` and `bun` carry `always`; `next`, `astro`, `expo` and `react` carry `never`. Asset specifiers keep their extension everywhere, because a bundler resolves them BY it, and `astro` keeps `.astro` for the same reason: Astro's `resolve.extensions` does not carry it, so a layout imported without it fails the build. A package's subpath is left to the package under `never` as it is under `always`: a package with no `exports` map resolves a subpath only by its file name — `expo/metro-config.js` in an ESM `metro.config.js` — so the spelling is the package's, and the rule judges the project's own specifiers alone. Both are `error` — a profile changes the convention, never the level.

## How the config is merged

The derived config is the platform's profile, then each preset's oxlint config, then the project's `typescript.oxlint`, merged deterministically, left to right ([the merge order](configuration.md#the-merge-order)):

| Keys                                                | Merge                                   |
| --------------------------------------------------- | --------------------------------------- |
| `extends`, `ignorePatterns`, `jsPlugins`, `plugins` | concatenated, duplicates dropped        |
| `overrides`                                         | concatenated, order kept, never deduped |
| `env`, `globals`, `options`, `rules`, `settings`    | shallow-merged, last wins per key       |
| anything else                                       | taken from the last config that sets it |

A workspace adds one block per member that declares itself: the member's own derived config, scoped to its folder as overrides after the root's — its rules, with every rule the root arms and the member's profile does not turned off, and its plugins — so each member is linted by its own platform from the one root config.

## Import boundaries

A layer map is not an oxlint fragment: `no-restricted-imports` reads a specifier's text, and a boundary is about where an import lands. The map is declared in `jterrazz.config.ts` and judged by dependency-cruiser — [Quality checks](quality-checks.md#the-architecture-layer-map-pass), the hexagonal map included.

### `import/no-cycle`

On in core, and worth knowing what it does not see: oxlint's implementation ignores type-only imports, so a value import one way and an `import type` back is invisible to it (oxc#20551).

## Fixers that lie

A fixer that changes MEANING is never applied unattended. The rules below stay armed — `check` reports them and a human answers them — and `fix` runs with each one allowed, so the rewrite never lands. Each is marked in the manifest with what its rewrite does, and this list is that mark's projection.

- `typescript/no-confusing-void-expression` — wraps a returned promise, after which nothing awaits it
- `typescript/no-unnecessary-type-assertion` — drops a cast a widened platform type needs
- `typescript/promise-function-async` — wraps a function that hands out an existing promise in `async … await`, so the caller receives a fresh promise nobody has claimed
- `unicorn/no-useless-promise-resolve-reject` — unwraps `Promise.resolve({ … })` in an arrow body into a bare object literal, which is a block

The same holds for oxlint's own suggestions: `typescript fix` runs `oxlint --fix`, never `--fix-suggestions` or `--fix-dangerously`. On this rulebook a suggestion removes the `console.log` that is a command's only output, rewrites `void promise()` to `undefined` and changes what an optional chain evaluates — run by hand, every one of them is a diff to read line by line.

### Module augmentation

An augmentation merges into an existing declaration only as an INTERFACE — a `type` alias redeclares the name, and every member of the original is lost — and the `export {}` beside it is what makes a file carrying `declare module` an augmentation rather than an ambient redeclaration. `typescript/consistent-type-definitions` is therefore off: every place it reported on the estate was one where the language needs an interface, and the one spelling it held prevents no defect. `typescript/no-useless-empty-export` stays on: it fires only where the file is already a module by another export, which is the case the `export {}` adds nothing to.

## The formatting decisions

100-char print width, 4-space indentation, single quotes, trailing commas everywhere, semicolons, LF. Those four do not move: twenty-eight repositories are written that way and two of them hold signed attestation bytes a reflow would invalidate.

The three sorters are law 4:

- **`sortImports`** — builtins and externals together, then internals, then the relative block, then styles; a blank line between groups, case-insensitive ascending inside one. It reorders import STATEMENTS and leaves the named specifiers inside one statement alone, which is why `perfectionist/sort-named-imports` stays on.
- **`sortPackageJson`** — on, scripts left in the order their author put them.
- **`sortTailwindcss`** — `class`, `className`, and the class-holding helpers (`clsx`, `cn`, `cva`, `tv`, `twMerge`, `twJoin`, `tw`).

perfectionist therefore keeps six rules, all of them about an order oxfmt does not touch: union types, intersection types, JSX props, heritage clauses, named imports, named exports.

## Size and complexity

Three caps, and each one counts a different property. `complexity` counts the paths through a function: 12, in its `modified` variant, where a `switch` counts once — a dispatch over a closed union is one decision, not one path per case. `max-lines-per-function` (60) and `max-lines` (300) count size, which complexity never did, since a long function can have a single path. Both count every line, comments and blank lines included, the way `spec-file-within-line-limit` counts. `max-statements` is off everywhere, covered by whichever cap bounds the file's functions: `max-lines-per-function` outside a test file, `@jterrazz/test`'s `test-body-within-line-limit` inside one — oxfmt writes one statement per line either way, so a line cap bounds the count.

A spec file's size has one judge. `@jterrazz/test`'s `spec-file-within-line-limit` holds every `*.spec.ts` to 400 lines, so `max-lines` is off there, scoped by the same suffix, and the two caps never judge one file. A module test (`*.test.ts`) is held to the same 400: its table tests list the cases of one module, and five of them ran 314 to 376 lines where the source's 300 left no seam to cut at. A `*.specification.ts` and every other file under `specs/` are code, and hold 300. A module test past 400 lines is answered by splitting the MODULE it tests: one module has one test file (`@jterrazz/test`'s `one-test-file-per-module`), so a second test file for the same module is refused, and a module whose test needs more than 400 lines holds more than one subject.

A test file's functions have one judge too. A test file holds one `describe` (`one-describe-per-file`), and that callback is a function as long as the file, so `max-lines-per-function` is off under the three suffixes that declare tests — `*.test.ts`, `*.test.tsx`, `*.spec.ts` — and `@jterrazz/test`'s `test-body-within-line-limit` caps what it would have caught there, a test body, at the same 60 lines. Every other file, a `*.specification.ts` included, holds its functions to 60.

## A data module holds data

A table of rows — every article's metadata, a taxonomy, a catalogue of projects — is long because the world it records is, and no split makes it short: one honest split of a 880-line catalogue still held 365. Its file name says what it is: `<subject>.data.ts`. `max-lines` stands aside for such a module, and `jterrazz-typescript/data-module-holds-data` keeps the exemption honest — a data module holds its imports, its types and the literals it exports, and refuses a function, an arrow, a class or a bare statement anywhere in it. The logic that reads the table — a lookup, a sort, a filter — lives in a module of its own that imports it, and holds the caps every module holds.

## An errors module holds one family

A closed family of errors — a base and the subclasses a caller tells apart — is one vocabulary, read together; one file per class scatters it. A module named `errors.ts` or `<subject>.errors.ts` is out of `max-classes-per-file`, and `jterrazz-typescript/error-family-shares-its-base` keeps that honest: one class of the module derives from something outside it — the base — and every other derives from a class declared there. A second root is a second subject, and moves to a module of its own.

## A focusable section is labelled

A region that scrolls is reached by the keyboard (WCAG 2.1.1), so `jsx-a11y/no-noninteractive-tabindex` lets a `<section>` take `tabIndex={0}` — the tag `jsx-a11y/prefer-tag-over-role` asks for in place of `role="region"`. jsx-a11y reads the tag alone, and a `<section>` is a region only when it is labelled: an unlabelled one is a stray tab stop a screen reader announces as nothing. `jterrazz-typescript/focusable-section-is-labelled` holds the exemption to its reason — a `<section>` carrying `tabIndex` names its region with `aria-label` or `aria-labelledby`. A negative `tabIndex` adds no tab stop — the section a fragment link or a script focuses, `tabIndex={-1}` — and is not read. A section whose props are spread from its caller is the caller's to label, and is not read.

## An accessible element is written in JSX

jsx-a11y reads the props of a JSX element and never the object handed to `createElement`. A polymorphic element built with `createElement(tag, { role: 'region', tabIndex: 0 })` therefore escapes every accessibility rule — the jterrazz-web pilot's first scroll-region atom did, and the exception it carried vanished from the Suppressions pass and the drift report with it. `jterrazz-typescript/accessible-element-is-jsx` refuses a `role`, a `tabIndex` or an `aria-*` prop written into the props object of a `createElement` call. The element is written in JSX — a polymorphic one as one branch per tag — so jsx-a11y reads it, and an exception it needs is a reasoned directive the drift report counts. Props handed in whole, as a variable or a spread, are the caller's and are not read.

## matchAll keeps no named group on Hermes

An `expo` app runs on Hermes, whose `String#matchAll` yields matches with no `groups`: `match.groups?.key` is `undefined` at runtime while the type check, and every test on Node, read the specification. `jterrazz-typescript/no-named-groups-in-match-all` refuses `matchAll` given a pattern with a named group, written in the call or held by a `const` of the same file; the groups of a global pattern are read with `exec` in a loop, or by position. The rule is on for the `expo` profile alone.

## A promise is awaited

The estate writes `await`: a promise read top to bottom, its failure caught where a `try` says so. `jterrazz-typescript/promise-is-awaited` refuses a `.then()`, `.catch()` or `.finally()` chain — unless it sits inside an `await` or a `yield` of its own function (`await Promise.all([task.catch(…)])`) or is returned whole — and an async function called where it is declared at the module's top level, since an ES module awaits there with no function to wrap it.

It owns the shape that `promise/prefer-await-to-then` and `unicorn/prefer-top-level-await` held between them, because both read the name `.catch` and never the type: a zod schema given a fallback, `z.string().catch('anonymous')`, failed them, and the mobile pilot rewrote its schemas into `safeParse` to pass. No promise takes a value in `.catch()`, so the rule reads a `.catch()` given one — a literal, an object, an array, `undefined`, a constant named in capitals (`DEFAULT_LANGUAGE`, imported or not, an enum's `Language.En`), or a `const` naming one — as no promise, and leaves it alone. A schema built from zod's import in the file — `z.string()`, or a `const` holding one — is no promise whatever its fallback, its lazy `.catch(() => value)` included. A schema imported from another module takes its fallback as a value: there, `.catch(() => value)` reads like a promise's handler, and is written with the value it returns.

## A comment no longer than its function

The default is no comment: the code speaks through its names, and a name that needs a comment is renamed instead. `jterrazz-typescript/comment-no-longer-than-its-function` holds the one shape that rule is broken by most: a docblock taller than the code it documents, which restates the code, argues it or tells its history.

It is this package's own rule, shipped as an oxlint JS plugin every profile loads, so a consumer declares nothing. It reads the comments directly above a function — a declaration, a function or arrow bound to a name, a method — as one run, where no blank line and no code separates them, and it counts every line that run spans, delimiters included. The body is the lines strictly inside its braces, or the lines of an arrow's expression, and never less than one. The rule refuses a run taller than the body, so a one-line comment always passes, and a three-line block needs three lines of body under it.

Two things are not judged. A directive (`oxlint-disable*`, `@ts-expect-error`) inside the run is not documentation, and does not count. A function the package PUBLISHES — exported from a file its `exports` map or `main` names, or re-exported from one through `export … from` — is read by a consumer in an editor's hover, where a sentence is what it is for.

Context that lives outside the codebase is the one comment the names cannot carry — a policy, a ticket, a decision maker, an external system's constraint. Where documenting it is truly necessary, the line says so, and the reason is required, as the Suppressions pass requires it of every directive:

```ts
// oxlint-disable-next-line jterrazz-typescript/comment-no-longer-than-its-function -- <the external context>
```

## A comment states its kind

A comment is kept for exactly one reason: it states what the code cannot. `jterrazz-typescript/comment-states-its-kind` makes that reason readable — every comment opens with the kind of thing it states, in lower case, followed by a colon:

| Kind         | States                                                                    |
| ------------ | ------------------------------------------------------------------------- |
| `invariant:` | what holds whatever path the code takes, and that the code relies on      |
| `hazard:`    | what breaks if the code is changed the obvious way                        |
| `outside:`   | a constraint or a fact that lives outside the codebase — a tool, a policy |
| `value:`     | why a value is this one and not another                                   |

```ts
// outside: the registry holds a deleted name 72 hours before it can be published again
export const NAME_HOLD_HOURS = 72;
```

A run of `//` lines states its kind once, on its first line; a `/* … */` block states it at its opening. Four shapes are not prose, and need no kind: a `/** … */` of one paragraph directly above an exported declaration, or above a member of one — a class's field or method, an interface's or a type's property, an enum member, a property of an exported object, outside a function's body — which is the symbol's hover in an importer's editor — its prose is wrapped at the formatter's width, with no blank line in it, and may be followed, on lines of its own, by the block tags an editor and typedoc render, `@param`, `@returns`, `@example` and its code, so a library keeps the documentation its consumers read; a hover of several paragraphs is refused, and nothing fixes it, since which paragraph is the symbol's is the author's; a directive another tool reads — `oxlint-disable*`, `@ts-expect-error`, `oxfmt-ignore`, `v8 ignore`, `@vite-ignore`, `Stryker disable`, `@__PURE__`, a triple-slash reference — whose reason follows it bare, since the directive is its own kind, and a kind written after it is refused; a lone lower-case language tag in a block comment set before a template literal — `/* sql */`, `/* html */`, `/* wgsl */` — which an editor reads to highlight the template; and every comment of a file whose first five lines carry `@generated`. A one-line `/** … */` above anything else — a private helper, a statement in a function body, an import — is prose like any other. A sibling package adds the openings its own tools read through the rule's `openings` option, as `@jterrazz/test` does for a test's `// Given -`, `// When -` and `// Then -` markers and its checker's directives.

A comment that fits none of these is refused where it opens. The answer is to delete it, or to rename what needed it — and where it does state what the code cannot, to say which. `typescript fix` never deletes a comment: the report carries its line, and the agent decides to keep it with its kind or to delete it. The one rewrite `fix` makes is lossless — a tool instruction that states a kind loses the kind. In TSX, a comment among JSX children is written `{/* … */}`: a `//` line there is JSX text, which oxfmt wraps as text.

`no-inline-comments` holds a comment to its own line, the inline shapes another tool reads where they stand aside — `@__PURE__`, `@__NO_SIDE_EFFECTS__`, `@vite-ignore`, a `webpack…:` magic comment and a language tag.

### Beyond the code

The same law holds every comment the repository writes, not only its code's: the [Comments (styles, scripts, YAML) pass](quality-checks.md#the-comments-styles-scripts-yaml-pass) reads a style sheet's `/* … */` — a `.css`, a `.scss` and the `<style>` of an `.astro`, `.svelte` or `.vue` file, a Sass `//` line too — and the `#` lines of a shell script, a Makefile, a Dockerfile and a YAML file, with the same four kinds and the same fix.

## Estate conventions the rulebook rests on

Several `off` reasons of kind `convention` name this page. Here is what they name:

- **An object orders by meaning**, not alphabetically — and generic inference is order-sensitive, so a sorted object is not the same program (`sort-keys`).
- **An export sits with the declaration it exports** (`import/exports-last`, `import/group-exports`).
- **A module exports what it owns by name**; a config file is a default export (`import/no-named-export`, `import/prefer-default-export`, `import/no-default-export`).
- **A relative parent import** is how a package reaches its own sibling module; a layer boundary is the map's job, not the path shape's (`import/no-relative-parent-imports`).
- **`null` is what the platform and JSON APIs return**; a codebase that refuses it grows a translation layer at every boundary (`unicorn/no-null`).
- **A one-shot CLI script has no event loop to protect** (`node/no-sync`), and configuration arrives from the environment at the edge (`node/no-process-env`).
- **The estate compiles to ESNext on Node 24**, where optional chaining and object spread are native syntax (`oxc/no-optional-chaining`, `oxc/no-rest-spread-properties`).
- **A spec states its assertions, not their count**, and the project's settings own the timeout once (`vitest/prefer-expect-assertions`, `vitest/require-test-timeout`).
- **A function with no behaviour is a test double's or a no-op adapter's.** A test double often answers by doing nothing, and a no-op adapter — `noop.adapter.ts`, or `noop-<port>.adapter.ts` beside its port's other adapters — is the null object a library hands its consumers' tests: it answers its port by doing nothing. `no-empty-function` is off in both, by their globs, and on everywhere else (`no-empty-function`): a callback that does nothing on purpose elsewhere is `() => undefined`.
- **A vitest file is `*.test.ts` or `*.spec.ts`, or lives under `specs/` or `__tests__/`; a file another runner owns takes that runner's suffix.** The vitest rules read every file the first three name as one of theirs, and a spec that shared the suffix would be handed vitest's `expect` in place of its runner's. A Playwright file is `*.e2e.ts`; a jest-expo render test is `*.render.tsx`. The first matches no vitest glob; the second sits under `__tests__/`, where the glob would take it, so the override that arms the vitest rules excludes it (`excludeFiles`), and nothing has to be ignored. Both stay in the type program; the production check reads a `*.render.tsx` as a test file, and knip takes it as an entry, so no repository relaxes the rules or lists the files itself. `vitest/consistent-test-filename` holds the first half as a FLOOR — this rulebook gives it both spellings and no third, where the rule's own default names `*.test.ts` alone and would ask a `specs/` tree to rename itself. Which of the two a repository writes where is `@jterrazz/test`'s, whose `test()` preset replaces the pattern with its own wherever a repository lists it.
- **A binding nobody reads is named `_`, and nothing longer.** `no-unused-vars` asks an unused name to start with an underscore, `no-underscore-dangle` refuses a leading underscore on every name but that one — `_` itself is the exemption both rules share, and no longer spelling satisfies the pair. It is the form a `using` disposable takes where the handle is never read again: `await using _ = await intercept(contracts);` gives the resource back at the scope end and says, by its name, that nothing else will touch it. A second one in the same scope is a second name, so the scope is the limit the idiom carries.
- **A forgotten `await` in a spec is a defect, not a style.** `typescript/await-thenable`, `typescript/no-floating-promises` and `typescript/no-misused-promises` sit in the base rulebook and no override relaxes them, so every vitest glob inherits all three through tsgolint. It is what Playwright recommends on a spec tree, and for the same reason: an async matcher returns a promise, and a spec that drops it passes by asserting nothing.

## Unused code (knip)

`typescript check` runs [Knip](https://knip.dev/) with a config it derives and hands over by path; a project keeps no `knip.json`, and the [Config (one file) pass](quality-checks.md#the-config-one-file-pass) refuses one. The derived config is this package's preset, then what the project's manifest and build already say, then the project's `typescript.knip`:

- `@jterrazz/*` packages ignored, and the toolchain's own binaries, which a consumer never declares.
- Convention paths ignored — `docs/`, and the ground a test stands on: `__fixtures__/`, `__expected__/`, `__seeds__/` and `__requests__/` wherever they sit, the four ground folders among the special `__<word>__` folders `@jterrazz/test` reads — the same four the oxlint profiles, the oxfmt preset and the tsconfig presets leave out; every one but the tsconfig presets, which JSON keeps literal, reads them from the roster in `lint/kit/project/ground.ts`. Its `__setup__/` is code, not ground: it is linted, formatted and typechecked like any source. At the root and inside every workspace member, because the convention belongs to the package.
- Plugin dependencies (`*-plugin-*`, `@scope/*`) ignored, and a declared package's DefinitelyTyped types (`@types/<name>`, `@types/<scope>__<name>`).
- Every entry the build compiles is an `entry` — the manifest's targets and the modules named for how they are loaded ([Building](building.md#what-the-manifest-does-not-name)) — so knip reads the same entry points the build does; a `*.cli.ts` anywhere is one too, a command run by its path, and so is a cli's `src/*.bin.ts`, which its bin or its compiled build runs.
- The editor files and `jterrazz.config.ts` are named as `entry`: the toolchain loads them and nothing imports them. So is every path a package preset loads by name from its own section — `@jterrazz/test`'s component project's `wrap` — which the preset names through its `entries`, so a project declares none of them. knip's own oxlint plugin is off, since the config it would read is derived.

What knip cannot trace is declared under `typescript.knip`, each path or name mapped to the reason it is named:

```ts
// jterrazz.config.ts
import { defineConfig } from '@jterrazz/typescript/config';

export default defineConfig({
    kind: 'api',
    platform: 'node',
    typescript: {
        knip: {
            ignoreDependencies: {
                'some-runtime-plugin':
                    'loaded by the bundler at runtime, never imported from source',
            },
        },
    },
});
```

The four keys are `entry`, `ignore`, `ignoreBinaries` and `ignoreDependencies`, each added to the preset's own. The config is derived from the project's `package.json` too, so one that does not parse is refused in four parts before knip runs, rather than leaving knip to judge the project against a config it never wrote.

### Workspaces

Knip is workspace-aware on its own: it reads the `workspaces` globs from your `package.json` and reports per member from a single run — which is why `check` invokes it once, at the root. A flat config's `entry` reaches the root workspace alone, so the derived config writes a `workspaces` section: the root's entries under `.`, and each member's under its folder — the preset's own, the member's build's, the paths its presets load by name, and its own `typescript.knip`, whose `entry` and `ignore` are read from the member's folder (`'src/{popup,worker}.ts'` in an extension member's settings). The root's `typescript.knip` `ignore` is resolved from the root, so a path it names inside a member carries the member's folder: `apps/api/src/generated/**`.
