# Test

A toolchain is proved by running it, against a real project on disk. Almost every test runs the built command in one of two ways. Most `cli` documents run `dist/command.js` through the pass selector, `specs/cli/__setup__/check-selection.cli.ts`, so that a spec runs only the passes it asserts on ([The self rules](#the-self-rules)). The `node`, `tsc`, `typescript` and `oxfmt` specs run the packed tarball, installed into a consumer's project as `npm install` would lay it ([The artefact a consumer installs](#the-artefact-a-consumer-installs)).

```bash
npm run build   # tsdown into dist/, which every suite below reads
npm test        # vitest — the unit tests and the specs
npm run lint    # this package's own CLI, run on this package
```

## Three projects, three speeds

`jterrazz.config.ts` declares three projects under `test.projects`, each built by `@jterrazz/test`'s helper of its specification — `unit`, `lint` and `cli` — and `vitest.config.ts` is the file `@jterrazz/test` derives from them:

| Project | Runs                                                                                     | Speed                                                                                      |
| ------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `unit`  | `src/`, `lint/` and `specs/surface/`                                                     | milliseconds for pure functions; seconds where a module's script is run as `check` runs it |
| `lint`  | everything under `specs/lint/` — a rule over a tree                                      | a second or two, one pass or one oxlint run per case                                       |
| `cli`   | everything under `specs/cli/` — the product command — `specs/kinds/` and `specs/shapes/` | seconds, real processes                                                                    |

A `cli` test has a budget of its own: the `cli` project's `timeout`, 120 s, in `jterrazz.config.ts`, where the preset gives every other test 30 s. What that project runs is the whole toolchain — the compiler, the type-aware linter, knip and every tree gate — once or twice per test, beside every other file of the project running at the same time. Its duration is therefore a fact about the machine's load more than about the run, and a budget cut to an idle machine fails a correct test on a busy one; 120 s holds two runs on a loaded machine, and a run that hangs still fails.

The same fact bounds what speeds the project up. Its wall time is held by the machine's CPU, not by how its files are cut, so the long serial files stay whole: running only the passes a spec asserts on ([the pass selector](#the-self-rules)) bought CPU time, and splitting would buy nothing more. No install is cached between runs and no `node_modules` template is shared: a sandbox copies the tarball the run packed, which the lockfile does not key, so a cache keyed on it would serve a stale toolchain.

The suffix says which project a file belongs to. A `*.test.ts` is a module test and sits in the `__tests__/` of its module's folder, which here is under `src/` and `lint/`, or is a meta-test of this package’s own and sits under `lint/self/corpus/__tests__/`; a `*.spec.ts` is the assembled product and sits under `specs/<specification>/`. `unit()` collects the first, `cli()` the second plus every `<case>.spec.yaml`, and the `cli` project states nothing of its own. `unit()` is the one that states its globs, because one tree it collects lives under `specs/` and the default set excludes that folder whole.

A rule is proven where its behaviour lives, on `@jterrazz/test`'s kit to test rules ([Rules kit](../reference/rules-kit.md#testing-a-rule)). Its visitor alone is a module test on `ruleTester()`, which refuses an invalid case that states no line and column — `lint/consumer/rules/comments/__tests__/comment-no-longer-than-its-function.test.ts`. What a rule or a pass says about a TREE is a lint spec, `specs/lint/<subject>/<aspect>.spec.ts`, on `specification.lint()`: the plugin as it ships (`comments-lint.specification.ts`), the Names and Architecture passes run as the checker runs them (`names-lint`, `architecture-lint`), and the base preset's laws alone, or beside a preset and a repository's own additions, through `presetChecks` (`preset-lint`, `declared-preset-lint`). Each compares the whole report — every finding at its `file:line:column`, with its lesson. What stays under `specs/cli/check/` is the command's own behaviour: which passes run, the sections they print, the ratchet, the drift report and the exit — and the command's own reading of `jterrazz.config.ts`, a preset declared there reaching the Architecture and Names passes (`presets-declared.spec.yaml`).

Whether a test exists at all — a module test kept, or a spec in its stead — is the constitution's: `@jterrazz/test`'s `docs/23-conventions.md`, "Which test earns its place".

The `unit` project is where a pure function is proved: the config merge (`lint/kit/compiler/__tests__/compile.test.ts`), the rulebook's builders (`lint/kit/compiler/__tests__/decision.test.ts`), and the manual's rules over in-memory trees (`lint/consumer/checks/__tests__/docs.test.ts`). Nothing there spawns anything but `make`, over stubs, where the `fix` recipe is proved; `npm pack` and `tar`, where the tarball is read as a consumer receives it and its bin is run once over an empty folder (`specs/surface/package/tarball.test.ts`), and `npm pack --dry-run`, where a self rule's home is held out of it (`lint/self/corpus/__tests__/audience.test.ts`); and `git`, where the tree every gate sweeps is read across index moves and live edits, and a build folder the index tracks is dropped from it (`lint/kit/project/__tests__/git-tree.test.ts`, `lint/kit/project/__tests__/project-files.test.ts`).

### `specs/surface/` — the repository suite

The files under `specs/surface/package/` read this package's own published tree rather than one module: `tarball.test.ts` and `builder-calls.test.ts` hold the split between the rules that ship and the rules that stay home — the first over the packed tree it shares with `shipped-links.test.ts`, `__setup__/packed-tree.ts`, the second over the sources that tree is built from ([below](#who-a-rule-is-for)) — and `makefile.test.ts` runs the `fix` recipe [Quality checks](../reference/quality-checks.md#the-six-gestures) hands consumers — and this repository's own — over stubbed fixers. `documented-examples.test.ts` compiles every TypeScript example of the README, the manual and the skill, each in a folder of its own under the file name its first line gives, with the compiler of the install `make test` lays from this build's tarball. None has a module to sit beside — each reads the whole package — and none reaches a runner, since nothing is served.

The rulebook suites read the whole rulebook the same way, through oxlint and oxfmt run directly, and sit in this suite too: `specs/surface/rulebook/` holds the two that read every profile's decisions at once, and a suite standing on ground of its own owns a domain beside it — `resolved-config/` its goldens, `fixpoint/` and `module-augmentation/` their fixtures, `tsconfig/` its consumers. What they share with the `cli` suites that drive the same tools — the profiles, the sandbox a profile is linted in, the astro stand-in — is `specs/__setup__/rulebook.ts` and `specs/__fixtures__/astro-package/`.

That shape is the THIRD DOOR the conventions name: a first-level folder under `specs/` that is no specification, covering a tree instead of a product served through an entry. `specification-test-uses-its-runner` and `specification-folder-has-its-runner` do not reach it, its files carry the unit's `.test.ts`, and `unit()` collects them by glob. `specs-at-declared-depth` still judges the shape, at the depth this project declares — the default — so the asset-less files group in a domain folder, `package/`, exactly as they would under a specification. The constitution owns the rule — `@jterrazz/test`'s `docs/23-conventions.md`, "The third door: a repository suite".

## A scenario is a document

`specs/cli/` drives the product command through `specification.cli()`, handed the selector below, which runs the built command — never a tool underneath it. Most scenarios are `<case>.spec.yaml` files rather than code:

```yaml
description: what the scenario claims # the vitest title
fixture: ./__fixtures__/gitignore/old-layout/ # the ground it stands on, by its path
runs:
    - command: check # the session, one entry per invocation
      exit: 1
      stdout: |
          …
```

`literate({ runner })` from `@jterrazz/test/vitest` binds every document of this repo to `cli.specification.ts`, the product runner. The format itself is `@jterrazz/test`'s, and the regeneration gesture is below.

Each `check` document states the **whole** combined output of the run, not the fragment it is about. Where a fixture makes a tool refuse for a reason the scenario is not about — a knip case with no tsconfig, so tsc prints its own manual — the document spans that block with `{{any}}` and a comment naming whose noise it is.

One block is spanned for good: oxlint's own report. The linter picks its form from the environment — GitHub workflow commands under `GITHUB_ACTIONS`, one compact line per diagnostic under an AI agent, miette's framed rendering elsewhere — and `check` prints the report in the form the linter picks, so its text is a fact about the machine, not about the run. No document states an oxlint diagnostic: the rulebook suites read `--format=json` through `diagnosticsOf`, and a `check` document claims the verdict our own passes print beneath the linter's block. What the block holds is proved once, by `specs/cli/check/oxlint-report.spec.ts`, against oxlint itself: in each form, over a file breaking a rule of every frame shape, the pass prints what oxlint prints alone.

## The rulebook has seven suites

The presets are the one part of this package a document cannot reach: `check` loads a preset from the consumer's `node_modules`, and a copied fixture has none. So the rulebook suites drive the tools directly, and seven of them divide the claim about what the rulebook decides between them: five read the rulebook itself and live in the repository suite, `specs/surface/` (above), and two take the consumer's view through the `cli` runner in `specs/cli/preset/` — the `cli-runs-the-product-binary` exception `oxlint.specification.ts` states. That folder's other suites — `composition`, `covered-by-testing`, `resolution`, `strict-install` — and `specs/surface/tsconfig/` prove how a preset composes, resolves and loads, not what it decides.

| Suite                 | Claims                                                                                                                                                          |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resolved-config`     | each profile resolves to the rule set its golden records, marker by marker                                                                                      |
| `rule-surface`        | every non-nursery rule of every loaded plugin is decided, every type-aware one too, and no `categories`; an `unsafe` mark sits on a fixer plain `--fix` applies |
| `fixpoint`            | oxlint's fixes and oxfmt's reach a fixed point — no rule fights the formatter                                                                                   |
| `behaviour`           | a fixture written to break rules reports exactly the diagnostics it should                                                                                      |
| `exclusive-pairs`     | every `off` of kind `exclusive` names a rule that really is on, and conflicts                                                                                   |
| `install-matrix`      | one consumer per profile installs under pnpm-strict and checks green                                                                                            |
| `module-augmentation` | a `declare module` block keeps the interface that merges, and its `export {}`                                                                                   |

The `install-matrix` suite is the outside view, and it is the one that fails when the corpus is wrong: six tiny projects, each the smallest honest consumer of one platform — a manifest, a `jterrazz.config.ts` declaring that platform, the derived files [Getting started](../start/getting-started.md#2-the-editor-files-are-derived) writes, one source file and one test file. The ground is `specs/cli/preset/__fixtures__/install-matrix/<platform>/`, and the platform IS the directory name, so a seventh platform earns a consumer by existing.

The `astro` consumer declares `astro`, because the preset it extends stands on Astro's own. What the runner links there is a stand-in, `specs/__fixtures__/astro-package/` — Astro's strict tsconfig and a CLI whose `check` has no template to refuse — at the consumer's root, and again beside the package in the sandbox's store, which sits outside the consumer where pnpm's would sit inside it.

### Regenerating a golden

Every golden of this repository takes the same gesture:

```bash
TEST_UPDATE=1 npm test
```

It rewrites the `__expected__/` trees, the resolved-config rosters, the catalogue section of [Lint presets](../reference/lint-presets.md), and the `stdout` of every spec document. Two things about it are worth knowing before reaching for it. A `{{any}}` token SURVIVES, but the real output is appended after it — so a document spanning a block it is not about is hand-edited, never regenerated. And the catalogue table comes out unaligned; `typescript fix` puts the columns back, and the freshness test compares cells, not padding.

## The artefact a consumer installs

What a consumer gets is the tarball, not `dist/`: the `cli` project packs the checkout once per run (`specs/cli/__setup__/packed/per-run.ts`) and unpacks it at `PACKED_PACKAGE`. The packing is `specs/__setup__/packed/pack.ts`'s, which the surface suite's packed tree reads too. Every install sandbox — the split install, the pnpm-strict one, the profile matrix, the toolchain whose versions a drift or doctor claim forges — copies that tree, never the folders it is built from, so a file `files` leaves out fails them as it would fail a consumer.

The consumer's own view is run by `packed-cli.specification.ts`: its runner lays the consumer's `node_modules/` as `npm install` leaves it — the package copied from the tarball, and hoisted beside it every package its `dependencies`, `optionalDependencies` and required `peerDependencies` reach, and those the consumer's own manifest declares, taken from this checkout's install, each one's bin linked into `.bin/` — then runs the consumer's command there, with that `.bin/` alone added to `PATH`. A devDependency of this checkout is not in that install, so an import the package does not declare fails there as it fails for a consumer, and a consumer fixture declares what it needs itself, such as `@types/node` for the node tsconfig preset. Each spec sits in the folder of the command it runs, from that install: `node/subpaths` loads every target of the exports map under its condition and reads the names each entry publishes, `tsc/declarations` compiles a consumer module against the published `.d.ts` — the config's augmentation, and every call it must refuse under an `@ts-expect-error` — `typescript/typescript` runs `check` and `fix` from the linked bin, and `oxfmt/oxfmt` formats a project through the installed preset.

### One project per kind

`specs/kinds/` proves every `kind` `jterrazz.config.ts` declares on a project of its own, written as a person writes one: under `specs/kinds/<kind>/__fixtures__/<kind>/`, a manifest, the declaration, its sources and tests, its manual and Makefile, and none of the files `fix` derives. Its runner, `specs/kinds/__setup__/specimen.ts`, lays the install `packed-cli.specification.ts` lays, with both packages of the family in it — this run's tarball of `@jterrazz/typescript`, and the `@jterrazz/test` this checkout installs, which is package-test's tarball — makes the folder a repository, then runs the sequence `<kind>.spec.ts` names: `typescript fix` from the bare declaration, the build where the toolchain builds the artefact, `typescript check`, and the project's own test command. The specs share the run's one pack, in the `cli` project. Which kind runs on which platform there, and which gestures each proves, is [Configuration](../reference/configuration.md#kind-and-platform)'s generated matrix; `lint/self/corpus/__tests__/kind-matrix.test.ts` fails a kind declared without its specimen, and a specimen standing for no declared kind. A monorepo is no kind, so its specimen stands beside them at `specs/shapes/monorepo/`: a root that lists one library member in `workspaces` and keeps no `jterrazz.config.ts`, run through the same runner and the same gestures from the root.

The repository installs itself too (`file:.`, a copy laid from its tarball), and `@jterrazz/test`'s specifications load `@jterrazz/typescript/rules` from that copy: before `make lint` and `make test`, `install-self` lays it again from the tarball of the build they stand on, so neither a spec nor the lint specification judges an install older than the checkout.

## When a chain of code is the right answer

Under `specs/cli/` every spec is a `.spec.ts` whatever door it takes — the suffix says the assembled product, not which runner reaches it. A document is still the default, and a chain of code is the exception; each one says which exception it is:

- **The binary is not the product.** oxfmt and oxlint run directly in the `behaviour` suite, and three install sandboxes run a script of their own under `specs/cli/__setup__/`, over the packed tarball — the split install, the pnpm-strict one that proves a consumer's configs load with one devDependency declared, and the profile matrix above.
- **The stream has no byte-exact form.** `dev/` waits on a marker instead.
- **The ground cannot be a fixture.** A fixture is what git tracks, and some ground git never tracks: a `.git`, an index holding one file and not another, an empty folder, a file the fixture's own `.gitignore` keeps out, a stub under `node_modules/`, an oxlint config this repository could not load. The `cli` runner's `.prepare()` lays it in the working directory after the fixtures — `specs/cli/__setup__/repository.ts` makes that directory a repository — so the gate claims that need one (committed artefacts, the Docs (layout) pass, the format and secrets sweeps, empty directories, the Makefile contract) are still chains with goldens. A package the spec's own project installs needs no step: `.link()` lays it — the build guard's claims link the `@jterrazz/test` this repository installs, since the guard judges only by the install the package resolves, and the drift claims link `@jterrazz/typescript`, so the config they stand on resolves the profile it names. A config oxlint would refuse as a NESTED one is the same case for a different reason. `typescript check` hands oxlint files and never reads a config under the ground ([Quality checks](../reference/quality-checks.md)), but `@jterrazz/test`'s checker, run alone as `make fix` runs it first, hands oxlint this repository whole, and oxlint loads every config in it: one that cannot load, one naming a root-only `options` key, or one registering a plugin name this repository's config already holds would fail that run, so a step writes it. A config that only ARMS rules over a deliberately broken tree is safe to commit, since the linter is handed no file of the ground it sits in, and a case needing a root-only option runs the default profile, which ships them.
- **The cwd must sit below the ground.** The gitignore gate's ancestor walk needs a `.gitignore` ABOVE the directory it runs in, and so does the claim that a config above a project with none of its own is never read: the chain runs `exec('check', { cwd: 'project' })` in a folder of a fixture that holds the ancestor.

Every spec under a specification folder reaches that specification's runner, which is what `specification-test-uses-its-runner` holds; the rulebook suites, which reach none, took the third door into `specs/surface/`.

## Where a fixture lives

What a spec stands on sits in the four ground folders `@jterrazz/test` reserves wherever a test stands on a file: `__fixtures__/`, `__expected__/`, `__seeds__/` and `__requests__/`. A fixture sits in the `__fixtures__/` of the lowest folder its readers share: `sample-app` and `incremental-app`, which several cli domains use, in `specs/cli/__fixtures__/`; one a single domain reaches for beside that domain, in `specs/cli/<domain>/__fixtures__/`; the specs root keeps a shared folder only for what several first-level folders share, as the astro stand-in the `cli` and surface suites both install. The code the specs share sits the same way in a `__setup__/` — `specs/cli/__setup__/`, `specs/surface/package/__setup__/`, and `specs/__setup__/` for the rulebook sandbox and the scratch directories every suite takes — the placement law `@jterrazz/test` holds. Either way a spec names it by its path from the spec file, spelled in full, and a string is never a path: a chain hands the disk over as `file()` or `directory()` — `.fixture(file('./__fixtures__/formatter/wrong-style.ts'))`, `.fixture(directory('../__fixtures__/sample-app/'))` — and a golden the same way, `toMatch(file('./__expected__/resolution.txt'))`. A document's `fixture:` takes the same paths, its trailing `/` saying which of the two it is: `fixture: ./__fixtures__/sample-lib/` spreads a directory. A stream compared as a value reads `result.stdout.text`.

The presets this repository ships ignore those four folders wherever they sit, and its own run takes them from the presets like any consumer: no ignore of its own in the lint scripts, `jterrazz.config.ts` or `tsconfig.json`.

The domains today: `build`, `check` (the command's passes and verdicts, each stating the whole run), `clean`, `dev`, `docs-layout` (the manual's rules, one document per family), `doctor`, `fix`, `help`, `node`, `oxfmt`, `preset`, `start`, `tsc`, `typescript`. Four of them run the packed tarball in a consumer's project, through `packed-cli.specification.ts`: `node`, `oxfmt`, `tsc` and `typescript`.

## Who a rule is for

Every rule this package holds declares its audience: `consumer`, meaningful in any project that uses the package, or `self`, this package's own suite discipline. Only consumer rules ship. A self rule lives in this repository's tests and its own configs, and this page is where it is described: the catalogue in [Lint presets](../reference/lint-presets.md) lists consumer rules alone, and `files` leaves this page out of the package, since describing a self rule names it.

### Where each rule declares it

A rulebook fragment declares `audience` for every decision it holds, from the closed pair `AUDIENCES` in `lint/kit/compiler/decision.ts`, and each catalogue entry carries it. Every other rule is a row of the manifest — `lint/consumer/catalogue/manifest.json` for a consumer row, `lint/self/catalogue/manifest.json` for a self one — on one of three channels: `checker`, a pass of `typescript check`; `runtime`, a refusal a shipped module throws, rejects or exits non-zero with; and `meta`, a meta-test. The package holds no type-level rule. A `self` row names its `home`, the path that holds it, and the `names` it goes by.

Every fragment, every pass and every refusal that ships is `consumer` today. The runtime rows that throw are the sweep refusing a tree it cannot read — a four-part refusal — and, in the command, the Knip pass refusing a project file its config is merged from that does not parse, and fix mode refusing a wrapper it cannot write, both four-part, and the knip merge refusing a preset of its own that does not parse and fix mode failing to load its fixer list, each an invariant. The rest exit: the checker program failing its verdict, a pass name it does not know or a read it cannot make, one row per exit that is not 0. The command itself exits through its launcher, which hands on the status the command returns, so its verdicts are no row.

An error a shipped module constructs is one of two forms, and `lint/self/corpus/refusals.ts` holds every module of `lint/` and `src/` that ships to it: what a project can cause is `new <Error>(refusal({ found, why, fix, read }))`, its read a heading of this manual that exists; what only the toolchain can cause is `invariant('<what broke>')`, whose message says the bug is the toolchain's. Both are built in `lint/kit/catalogue/lesson.ts`, the one module the audit leaves out; any other construction of an error — `new` on an error class, a class extending one included, or a built-in called bare — fails it, as does a refusal whose `read` is not written in place and a chapter anchor naming a heading no chapter has. The audit parses each module with the TypeScript compiler API, the same judgement `@jterrazz/test` makes of its own source, and a failure prints each finding at its `path:line:column`, in four parts, under `error-is-a-refusal-or-an-invariant`.

A decision's two invariants — a level is `error` or `off`, and an `off` carries one of the five reasons naming what carries it, as an unsafe fixer names what its rewrite changes — judge this package's fragments alone, since `fragment()` is not exported: `lint/kit/compiler/decision.ts` builds and enforces nothing. The walk imports every module of `lint/` and `src/` but the tests, and collects every fragment anywhere in what each exports, by default or by name, whether a profile carries it or not. It leaves out `lint/kit/testing/`, which runs a child when imported — the folders the self corpus hands it with the walk, `FRAGMENT_WALK`. The module walk reaches the built tree: it imports one module in a child of its own, with the `fragment` builder of the tree wrapped, before its module runs, to record what it builds, the process's exit refused, and a bare command line in an empty directory. What the module exports and what its import built are both judged.

A fragment with no id is a self rule the audit names: no consumer reaches `fragment()`, since no builder of a fragment ships.

The catalogue itself ships, since `fix` reads its unsafe fixers; the table and the fixer list [Lint presets](../reference/lint-presets.md) carries between its `GENERATED` markers are rendered from the consumer entries alone.

The selector is `TYPESCRIPT_CHECK_PASSES`, a comma-separated list of pass keys, and the shipped command holds no copy of it: `main()` runs every pass unless its caller hands it a selection, and the bin that ships, `src/typescript.bin.ts`, hands none. The specs run the product command through `specs/cli/__setup__/check-selection.cli.ts`, exported as `SELECTING_BIN` by `specs/cli/__setup__/check-passes.ts`: the `cli` runner for every document, and each chain that spawns the check with `onlyPasses()`. It hands every run to the built command, and when the variable names passes, a selection answering for those alone. A pass the selector leaves out prints nothing and weighs nothing in the verdict, and a key that names no pass fails the run with the list of keys, the passes the command declares in its report order. A pass left out does not run at all: no pass reads another's output. The specs prove what a run reports and its verdict, not which passes it launches: leaving a pass unlaunched is what saves the time, and no spec goes red if it starts again. The spec documents, apart from the three `passes-*.spec.yaml` that prove the selector, and a chain that names no pass, run every pass.

### What holds the split

`lint/self/corpus/__tests__/audience.test.ts` reads this checkout's catalogues. Every manifest row declares an audience, as every fragment does beside the decision invariants, over the same walk, and every row sits on a channel under an id of its own. Every profile is compiled from consumer fragments alone. The consumer checker rows are exactly the passes the command declares, `CHECK_PASSES`. A shipped module of `lint/`, `src/` or `bin/` refuses as often as its runtime rows declare, counted off its text per way: a throw of an error it builds, `throw new X(` or `throw X(`; a `reject(`, whatever it rejects with; and an exit with anything but 0, as `exit(`. A rethrow of a caught error forwards a refusal and is not counted, nor is an error built on one line and thrown by name on another. Each row is still worded so there. `specs/surface/package/tarball.test.ts` reads what npm would publish, judging content and never names. No `*.test.*` or `*.spec.*` ships. The walk sees what an import builds, not what a builder builds when a consumer calls it later, so `specs/surface/package/builder-calls.test.ts` reads the text the bundle is compiled from: every call a shipped module makes to `fragment()` hands it an object literal whose `audience` is a string literal, with no spread; a namespace import or a re-export of `kit/compiler/decision.ts`, or the builder handed on as a value, fails it. Every command the `bin` installs runs over an empty folder: bare, then under the specs' selection and every variable the packed modules read naming a pass; then handed each flag the packed command spells, followed by a pass. Each run reports the same passes to the same verdict as the bare one. What the proof does not reach is a choice read from somewhere else: a file the project holds. ## The self-lint is the strongest test

`npm run lint` is `typescript check` run on this repository, so the package is the first consumer of every gate it ships:

- the **Docs (layout)** pass reads this repo's own `docs/`, which is why the pages you are reading are cut into the sections the rule demands;
- `oxlint.config.ts` loads the `@jterrazz/test` ESM plugin and this package's own built profiles through the exports map, and `check` type-checks `specs/`, `src/` and `lint/` — a broken exports map fails the lint, not a consumer;
- the Architecture pass holds this repository to the base preset's laws, the direction of `lint/` [Architecture](../concepts/architecture.md#the-judging-layer) draws — `kit/` importing no declaration, each consumer folder the catalogue and the kit alone, the shipped `lint/` importing neither `self/` nor `src/`, and `src/` no `self/` — so an import against it fails that pass, at its line.

A change that passes `npm test` but not `npm run lint` is not finished.
