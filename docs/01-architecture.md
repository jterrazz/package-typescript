# Architecture

One devDependency holds a project's whole toolchain, and this chapter says what is inside it.

The package is two sides that never mix: `lint/` JUDGES — every rule, every pass, every verdict a project can receive — and `src/` RUNS — the command that orchestrates processes, the config presets a consumer's own files extend, and the importable surface for what code has to reach directly. Both are TypeScript, built into `dist/`, which is what ships.

| Layer          | Holds                                                                                                                                          | Reached by                                                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lint/`        | every judgement: the declarations a project is held to, and the engine that runs them                                                          | `src/`, and a consumer through `./oxlint`, `./config`, `./rules` and `./docs`                                                                              |
| `src/command/` | the command — a module per concern (build, baseline, doctor, …), `check/` for the passes                                                       | the bin, and the spec harness's selecting launcher ([Testing](https://github.com/jterrazz/package-typescript/blob/main/docs/03-testing.md#the-self-rules)) |
| `src/presets/` | tsconfig, tsdown, oxlint, oxfmt and knip configurations                                                                                        | a consumer's config files, by `extends` or path                                                                                                            |
| `src/`         | the entries — `.`, `./oxfmt`, `./tsdown/build`, `./tsdown/bundle`, and `typescript.bin.ts`, the bin that hands the command line to the command | a consumer's `import`, and the `typescript` binary                                                                                                         |

The code the package ships sits under `src/` and `lint/`, both spine folders ([Repo structure](08-repo-structure.md)), and the `typescript` bin is built with the rest: a registry install links the command from `dist/typescript.js`. `dist/` is the build's product, ignored by git and published ([Building this package](#building-this-package)).

## The judging layer

`lint/` has one tree in every repository of the estate, and the Names pass holds every consumer to it ([Quality checks](06-quality-checks.md#the-lint-tree)). It is split by audience first: only modules sit at its root — the entries, named by [the entry grammar](06-quality-checks.md#the-entry-grammar), the checker program, and the compositions `src/` reads — and each folder below is one of three.

| Entry or folder of `lint/` | Holds                                                                                                                                                                                                                                                                       |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `index.oxlint.ts`          | the `./oxlint` entry, and the one place consumer/ meets engine/ for the rulebook: the six profiles of `consumer/rulebook/profiles.ts` compiled by `engine/compiler/compile.ts` with the path of this package's own plugin, `compose()`, `nested()`, oxlint's `defineConfig` |
| `checker.ts`               | the checker program the command runs every node pass through: it hands the passes of `consumer/checks/`, and which of them the baseline holds, to `engine/checker/`                                                                                                         |
| `index.docs.ts`            | the `./docs` entry: the manual's rules of `consumer/checks/docs.ts`, re-exported with their types                                                                                                                                                                           |
| `index.config.ts`          | the `./config` entry: the base preset, `typescript()`, composed from `consumer/catalogue/preset.ts`, the preset types, and the settings file's own — `JterrazzConfig` and its sections                                                                                      |
| `base-presets.ts`          | `BASE_PRESETS`, the base preset alone, which the checker, the kit and the default oxlint config resolve every settings file with                                                                                                                                            |
| `index.rules.ts`           | the `./rules` entry: the kit — the engine a sibling package writes its rules with ([Rules kit](09-rules-kit.md)); `index.rules.browser.ts` its half that reads no disk, served under the `browser` condition                                                                |
| `unsafe-fixers.ts`         | the unsafe fixers of every profile, which `src/command/unsafe-fixers.ts` turns off for the fixing run                                                                                                                                                                       |
| `consumer/`                | the declarations every consumer is held to, and nothing else — `catalogue/`, `rulebook/`, `rules/`, `checks/`                                                                                                                                                               |
| `self/`                    | the declarations only this repository is held to, never shipped — `catalogue/`, `rules/`, `checks/`, `corpus/`, and the modules where they are composed with the engine, when there is one to compose                                                                       |
| `engine/`                  | what runs the declarations and knows none of them — `project/`, `baseline/`, `checker/`, `catalogue/`, `compiler/`, `testing/`; it receives what it runs from a module at the root of `lint/`, and never imports `consumer/` or `self/`                                     |

"Engine" names this folder and nothing else: the `typescript` binary and `src/command/` behind it are **the command**, which runs the engine and the checks.

Two laws keep the audiences apart. **Declarations only:** `consumer/` and `self/` hold a rule, a check, a decision on an upstream rule, a catalogue entry, or their tests — a module there runs as no program, hands another module no function but one named for its file, and code the declarations share is the engine's; the Names pass refuses the rest ([Quality checks](06-quality-checks.md#the-lint-tree)). **The engine knows no declaration:** it is handed the profile table, the rows, the fragments, the passes and the plugin paths, and a module at the root of `lint/` composes them.

An import in `lint/` goes one way, the same in every repository that keeps the tree: `engine/` imports nothing of `consumer/`, `self/` or `src/`; `consumer/catalogue/` only `engine/`, since it is data at the bottom — here the base preset's data, `preset.ts`, which `lint/index.config.ts` composes, beside JSON rows the self corpus holds each printed id and sentence to and renders into the chapters; `consumer/rulebook/`, `consumer/rules/` and `consumer/checks/` the catalogue and `engine/`, never each other; the entry any of them. Inside `self/` the arrow is the same: `self/catalogue/` only `engine/` and the consumer catalogue it extends; `self/rules/`, `self/checks/` and `self/corpus/` its catalogue, `consumer/` and `engine/`, never each other. A catalogue's own tests are test material, and read the declarations they audit. Nothing shipped imports `self/`, and `src/` reaches no declaration of `consumer/` or `self/` — only `engine/` and the modules at the root of `lint/`. The base preset declares each arrow as a law of its own, so every repository that keeps a `lint/` tree is held to it with no line of its own, and the Architecture pass holds the resolved import graph to it ([Rules kit](09-rules-kit.md#the-base-preset)).

`lint/` and `src/` import each other one way only, and a module both need has one owner — the side whose behaviour it defines. Here `src/` is the command that runs `lint/`, so `src/` imports `lint/` through the modules at its root and `engine/` alone, never `self/`. `self/`, never shipped, may read `src/`: it judges the repository's own product; the shipped `lint/` never reads `src/`, though its tests, which are not shipped, may run a rule through the package that ships it. The same law holds in `@jterrazz/test`.

The rulebook is a manifest, not a config: one fragment per plugin, stating a decision per rule, and this package's own suite refusing a fragment that breaks either invariant — a level is `error` or `off`, and an `off` carries one of five recorded reasons ([Testing](https://github.com/jterrazz/package-typescript/blob/main/docs/03-testing.md#who-a-rule-is-for)).

Three steps and nothing between them. `lint/consumer/rulebook/profiles.ts` says which fragments each profile carries; `lint/engine/compiler/compile.ts` turns a fragment into the plain oxlint config object oxlint itself reads, and merges those objects; `lint/index.oxlint.ts` compiles the table, and a consumer imports its profile from there by name. `src/presets/oxlint/profiles/<name>.ts` re-exports one profile as a default export, no consumer's to reach — oxlint loads a config handed by path through its default export, so a profile oxlint is handed is a file of its own: the six under `dist/presets/oxlint/profiles/` are what the drift report prints each profile from. `src/presets/oxlint/declared.ts` is the one `check` hands a project with no config of its own: the config `fromPresets` composes from the `jterrazz.config.ts` of the directory oxlint runs in, or from the base preset alone where that file cannot be resolved — the pass that reads it refuses it. The rule decisions are [Lint presets](07-lint-presets.md)'s, catalogued there from the same manifest.

## Building this package

The package is TypeScript, and what ships is its build: `npm run build` runs tsdown over `tsdown.config.ts` into `dist/`, which git ignores and `files` publishes, with the JSON presets beside it as data, served where they are written. Every entry of the exports map, the checker program, the oxlint plugin and each preset a tool is handed by path are entries of the build; each carries the declaration tsdown generates from its source, so a type has one owner.

A build step is a precondition like an install: `make build` precedes `make lint` and `make test`, and the specs drive the built command. The toolchain builds itself with the tsdown it ships to everyone else, so there is no second toolchain, only the order of two gestures.

## The command

`typescript check` runs up to fifteen passes, most of them separate processes — tsc, oxlint, oxfmt, knip, publint, dependency-cruiser and the checker program of this package's own. The command starts them all, awaits each, and reports each in one fixed order ([Quality checks](06-quality-checks.md)); a pass whose answer is this package's own code — the knip config merged, the sweep a tool is handed — runs in the command itself, as a function; a tool's own output, oxlint's included, is printed as the tool printed it.

The rule the split follows: **the command decides whether a gate applies; the checker decides what the gate says.** Whether a `.gitignore` exists, whether a repository is a repository, which workspace members own a `specs/` — those are the command's probes. What is wrong with a `.gitignore`, or with a `docs/` tree, is a pass's, because the answer needs parsing and a rule roster.

A refusal the command's own code can meet from a project — a map it cannot compile, a tree its sweep cannot read — is thrown in four parts, `found: … · why: … · fix: … · read: …`, the read a heading of this manual; one only the toolchain can cause is `invariant()`, whose message says the bug is the toolchain's ([Testing](https://github.com/jterrazz/package-typescript/blob/main/docs/03-testing.md#who-a-rule-is-for)).

## The importable surface

The `.` entry (`src/index.ts`) and seven subpaths, all declared in the exports map — each a built `.js` beside the `.d.ts` the build generates:

| Subpath                              | Exports                                                                                                                                                                                                                                       |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@jterrazz/typescript`               | the `.` entry (`src/index.ts`) — `{ oxfmt, oxlint }` presets                                                                                                                                                                                  |
| `@jterrazz/typescript/oxlint`        | the six profiles, `compose()`, `nested()`, `fromPresets()`, `defineConfig`                                                                                                                                                                    |
| `@jterrazz/typescript/oxfmt`         | `base`, and oxfmt's own `defineConfig`                                                                                                                                                                                                        |
| `@jterrazz/typescript/docs`          | `auditDocs()` — the manual's rules, pure — and `HEAD_LINES`, how many opening lines of a file they read                                                                                                                                       |
| `@jterrazz/typescript/config`        | `defineConfig()`, `typescript()`, `definePreset()`, `JterrazzConfig`, `TypescriptSettings`, `ArchitectureSettings`, `ArchitectureRule`, `NamesRule`, `Preset`, `OptOut` and `ProfileName` — the family's settings file and its presets, typed |
| `@jterrazz/typescript/rules`         | the kit a package writes its rules with: the lesson, the rule and the check, the chapter projection, the baseline and its judges, the readers of a project ([Rules kit](09-rules-kit.md))                                                     |
| `@jterrazz/typescript/tsdown/build`  | the application build preset, and tsdown's `UserConfig` type                                                                                                                                                                                  |
| `@jterrazz/typescript/tsdown/bundle` | the library bundle preset, and tsdown's `UserConfig` type                                                                                                                                                                                     |

The oxlint entry carries the six profiles by name — `node`, `next`, `astro`, `expo`, `bun`, `react` — plus two things about composing them: `compose()` merges configs left to right, and `nested()` strips the root-only options from a profile a subtree's own config ships ([Developing](02-developing.md#a-subtree-on-another-profile)). A layer map is not a lint fragment: it is declared in `jterrazz.config.ts` and judged by dependency-cruiser ([Quality checks](06-quality-checks.md#the-architecture-layer-map-pass)). Each config TYPE — `OxlintConfig`, `OxfmtConfig` — is re-exported from the tool that owns it, never restated here: a hand copy drifts, and a drifted copy stops a consumer's own config from type-checking.

Each one re-exports the underlying tool's `defineConfig` on purpose: a consumer's config file names `@jterrazz/typescript` and nothing else, which is the one-devDependency contract holding under pnpm's strict `node_modules` ([Developing](02-developing.md)). The specs under `specs/cli/node/` and `specs/cli/tsc/` install the packed tarball into a consumer's project, load every subpath by its public specifier under each condition, and compile a consumer module against the published declarations — the package is its own consumer #1.

`./config` types the one settings file of the whole family, `jterrazz.config.ts` ([Developing](02-developing.md)), and the presets it lists ([Rules kit](09-rules-kit.md#presets)). `JterrazzConfig` is an interface so that each sibling package adds its own section by merging into it — `@jterrazz/test` declares `test` — and this entry never names a section it does not read.

`./rules` is the engine of `lint/`, exported: what a sibling package needs to write a rule, a check, its chapter and its debt the way this package does, so the family keeps one copy of each ([ADR-016](decisions/016-one-engine-writes-every-rule.md)).

`OXLINT_CONFIG_NAMES`, on `./rules`, is the one list of the names a project's own oxlint config may take. `check` and `fix` read it to decide whether a project has a config or is handed the default, the drift report reads it to say which, and `@jterrazz/test`'s checker reads it from the kit rather than from a copy, so it counts a config exactly where this toolchain does. It has no subpath of its own: a subpath only a sibling package reads is a line of the kit that sibling already imports.

`./docs` is the odd one out: it is not a config, it is a gate's rules, exported because that gate has two readers. `typescript check` reads a project it is installed in; an estate sweep reads clones it has installed nothing into. One pure function over a plain tree, and the rule ids, sentences and rosters stay in one executable copy. Its second reader is the estate's own CLI, not a sibling package, which is why it keeps a subpath of its own rather than a line of `./rules`.

## Two TypeScript compilers, on purpose

`typescript check` type-checks with the official TypeScript 7 Go compiler, pulled in through the per-platform `@typescript/typescript-*` optionalDependencies and resolved by path by the command.

The ordinary `typescript` dependency stays on ^6 because two consumers need the JavaScript compiler API that the Go package no longer ships: `dependency-cruiser` (a `typescript <7` peer) and `eslint-plugin-perfectionist`, which does a bare `require('typescript')`.

**Never add `typescript@7`, or an npm alias of it, to this tree.** Under pnpm's hoist fallback it can hijack perfectionist's lookup and fail intermittently with `isExternalModuleNameRelative is not a function`.

## The unit is the workspace package

Every per-package gate measures from the nearest `package.json`, never from the repository: a workspace root runs those gates once per member, and a single-package project is the one run it always was. `lint/engine/project/workspace-members.ts` answers what the members are, and every caller asks it rather than guessing.

The one gate that measures from the repository instead is the manual's, because a manual answers for a whole tree ([Quality checks](06-quality-checks.md)).
