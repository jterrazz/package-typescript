# Architecture

One devDependency holds a project's whole toolchain, and this chapter says what is inside it.

The package is two sides that never mix: `lint/` JUDGES — every rule, every pass, every verdict a project can receive — and `src/` RUNS — the command that orchestrates processes, the config presets a consumer's own files extend, and the importable surface for what code has to reach directly. Both are TypeScript, built into `dist/`, which is what ships.

| Layer          | Holds                                                                                                                            | Reached by                                                                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bin/`         | `typescript.js`, the launcher of a few lines that hands the command line to the built command                                    | the `typescript` binary                                                                                                                                   |
| `lint/`        | every judgement: the declarations a project is held to, and the engine that runs them                                            | `src/`, and a consumer through `./oxlint`                                                                                                                 |
| `src/command/` | the command — a module per concern (build, baseline, doctor, …), `check/` for the passes, `report/` for oxlint's report as drawn | `bin/`, and the spec harness's selecting launcher ([Testing](https://github.com/jterrazz/package-typescript/blob/main/docs/03-testing.md#the-self-rules)) |
| `src/presets/` | tsconfig, tsdown, oxlint, oxfmt and knip configurations                                                                          | a consumer's config files, by `extends` or path                                                                                                           |
| `src/`         | the importable entries — the barrel, `./config`, `./oxfmt`                                                                       | a consumer's `import`                                                                                                                                     |

The code the package ships sits under `src/` and `lint/`, both spine folders ([Repo structure](08-repo-structure.md)). `bin/` is the one root beside them, and it is npm's: a package's `bin` entry is where a registry install links the command from. `dist/` is the build's product, ignored by git and published ([Building this package](#building-this-package)).

## The judging layer

`lint/` has one tree in every repository of the estate, and the Names pass holds every consumer to it ([Quality checks](06-quality-checks.md#the-lint-tree)). It is split by audience first: only `index` files sit at its root — the entry, its declaration, its test, the checker program and the two parts `src/` and `./docs` reach through — and each folder below is one of three.

| Entry or folder of `lint/` | Holds                                                                                                                                                                                                                                                                                                |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `index.ts`                 | the `./oxlint` entry, and the one place consumer/ meets engine/ for the rulebook: the six profiles of `consumer/rulebook/profiles.ts` compiled by `engine/compiler/compile.ts` with the path of this package's own plugin, `compose()`, `layers()`, `hexagonal`, `nested()`, oxlint's `defineConfig` |
| `index.checker.ts`         | the checker program the command runs every node pass through: it hands the passes of `consumer/checks/`, and which of them the baseline holds, to `engine/checker/`                                                                                                                                  |
| `index.docs.ts`            | the `./docs` entry: the manual's rules of `consumer/checks/docs.ts`, re-exported with their types                                                                                                                                                                                                    |
| `index.unsafe-fixers.ts`   | the unsafe fixers of every profile, which `src/command/unsafe-fixers.ts` turns off for the fixing run                                                                                                                                                                                                |
| `consumer/`                | the declarations every consumer is held to, and nothing else — `catalogue/`, `rulebook/`, `rules/`, `checks/`                                                                                                                                                                                        |
| `self/`                    | the declarations only this repository is held to, never shipped — `catalogue/`, `rules/`, `checks/`, `corpus/`, and an `index` where they are composed with the engine                                                                                                                               |
| `engine/`                  | what runs the declarations and knows none of them — `project/`, `baseline/`, `checker/`, `catalogue/`, `compiler/`, `testing/`; it receives what it runs from an index, and never imports `consumer/` or `self/`                                                                                     |

"Engine" names this folder and nothing else: the `typescript` binary and `src/command/` behind it are **the command**, which runs the engine and the checks.

| Folder                | Holds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `consumer/catalogue/` | `manifest.json`, the consumer rows of the manifest; `findings.json`, every id a pass or a rule prints, with its family and the one sentence it holds a project to, rendered into the id tables of [Quality checks](06-quality-checks.md) — a refusal of the run rather than of the project (`baseline-ratchet`, `baseline-unreadable`, `oxlint-config-unparsed`, `oxlint-config-commonjs`) belongs to no family, prints a bare id and is not one of them; `families.json`, the closed list of those families |
| `consumer/rulebook/`  | one fragment per plugin, `frameworks/` for what a framework profile adds, `hexagonal.ts` the layer map this package ships, `profiles.ts` the table of the six                                                                                                                                                                                                                                                                                                                                                |
| `consumer/rules/`     | the lint rules this package writes itself, one file per rule under the folder of its family, assembled by `plugin.ts` into one oxlint JS plugin, built to `dist/plugin.js`, which `rulebook/jterrazz-typescript.ts` turns on by name — the index hands the compiler where it lives                                                                                                                                                                                                                           |
| `consumer/checks/`    | one file per pass of `typescript check` that needs more than a process spawn — what one file cannot see: the tree, the manual, the directives, the prose. A pass is a declaration the checker runs: its ids, its sentences and the findings it judges over what the engine reads; a part named `<pass>.<part>.ts` (`names.lint-tree.ts`) is its pass cut in two                                                                                                                                              |
| `self/catalogue/`     | the self rows of the manifest, and nothing else                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `self/checks/`        | `lint-direction.ts`, the layer map holding each arrow of `lint/` and between `lint/` and `src/`                                                                                                                                                                                                                                                                                                                                                                                                              |
| `self/corpus/`        | the meta-tests that hold the package to its own catalogue and rulebook, each beside the module declaring what it audits, and the projection table naming which renderer fills which chapter of this repository                                                                                                                                                                                                                                                                                               |
| `engine/project/`     | how a check or a rule reads a project: the sweep, the comment reader, the functions and values a module exports, the workspace members, the settings file, the entries, the built chunks, the test-material reader, the installed tool versions, the `docs/` tree, the resolved oxlint config                                                                                                                                                                                                                |
| `engine/baseline/`    | the `typescript` section of `jterrazz.baseline.json`: counted off a linter's report — `counts.ts`; read, judged exactly, lowered by `fix` — `section.ts`                                                                                                                                                                                                                                                                                                                                                     |
| `engine/checker/`     | the one runner and command line of the node passes: `checker.ts` reads the command line, runs the pass it is handed over what the engine reads, prints and reports its findings, judges a held pass against the baseline and writes a fix; beside it the commands of the engine's own — `baseline.ts` the `baseline` command, which judges the Oxlint pass against that section or writes it, `architecture.ts` the dependency-cruiser run, `project-queries.ts` what the command asks of a project          |
| `engine/catalogue/`   | the catalogue read and rendered: the families a unit's own catalogue declares, every decision of a profile table as one list with the unsafe fixers `fix` refuses, every id a set of passes and a plugin print, and the tables a projection renders                                                                                                                                                                                                                                                          |
| `engine/compiler/`    | the rulebook built and compiled: `decision.ts` the builders and the closed vocabularies, `compile.ts` the compiler, `layers.ts` the layer-map compiler                                                                                                                                                                                                                                                                                                                                                       |
| `engine/testing/`     | the walks the meta-tests share, which ship nowhere                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

Two laws keep the audiences apart. **Declarations only:** `consumer/` and `self/` hold a rule, a check, a decision on an upstream rule, a catalogue entry, or their tests — a module there runs as no program, hands another module no function but one named for its file, and code the declarations share is the engine's; the Names pass refuses the rest ([Quality checks](06-quality-checks.md#the-lint-tree)). **The engine knows no declaration:** it is handed the profile table, the rows, the fragments, the passes and the plugin paths, and an index composes them.

An import in `lint/` goes one way, the same in every repository that keeps the tree: `engine/` imports nothing of `consumer/`, `self/` or `src/`; `consumer/catalogue/` only `engine/`, since it is data at the bottom — here JSON rows no pass or rule imports, which the self corpus holds each printed id and sentence to and renders into the chapters; `consumer/rulebook/`, `consumer/rules/` and `consumer/checks/` the catalogue and `engine/`, never each other; the entry any of them. Inside `self/` the arrow is the same: `self/catalogue/` only `engine/`; `self/rules/`, `self/checks/` and `self/corpus/` its catalogue, `consumer/` and `engine/`, never each other. Nothing shipped imports `self/`. `lint-direction`, a `layers()` map in `self/checks/lint-direction.ts` that `self/index.ts` compiles — built to `dist/self.js`, which the build keeps out of the tarball — and `oxlint.config.ts` composes, holds each arrow.

`lint/` and `src/` import each other one way only, and a module both need has one owner — the side whose behaviour it defines. Here `src/` is the command that runs `lint/`, so `src/` imports `lint/` through its `index` files and `engine/` alone, never `self/`. `self/`, never shipped, may read `src/`: it judges the repository's own product; the shipped `lint/` never reads `src/`. The same law holds in `@jterrazz/test`.

The rulebook is a manifest, not a config: one fragment per plugin, stating a decision per rule, and this package's own suite refusing a fragment that breaks either invariant — a level is `error` or `off`, and an `off` carries one of five recorded reasons ([Testing](https://github.com/jterrazz/package-typescript/blob/main/docs/03-testing.md#who-a-rule-is-for)).

Three steps and nothing between them. `lint/consumer/rulebook/profiles.ts` says which fragments each profile carries; `lint/engine/compiler/compile.ts` turns a fragment into the plain oxlint config object oxlint itself reads, and merges those objects; `lint/index.ts` compiles the table, and a consumer imports its profile from there by name. `src/presets/oxlint/profiles/<name>.ts` re-exports one profile as a default export, no consumer's to reach — oxlint loads a config handed by path through its default export, so a profile oxlint is handed is a file of its own: `dist/presets/oxlint/profiles/<name>.js` is the one `check` hands a project with no config of its own, and the six are what the drift report prints each profile from. The rule decisions are [Lint presets](07-lint-presets.md)'s, catalogued there from the same manifest.

## Building this package

The package is TypeScript, and what ships is its build: `npm run build` runs tsdown over `tsdown.config.ts` into `dist/`, which git ignores and `files` publishes, with the JSON presets and the config-name list beside it as data, served where they are written. Every entry of the exports map, the checker program, the oxlint plugin and each preset a tool is handed by path are entries of the build; each carries the declaration tsdown generates from its source, so a type has one owner. The self rules build to `dist/self.js`, which this repository's own `oxlint.config.ts` composes and `files` leaves out.

A build step is a precondition like an install: `make build` precedes `make lint` and `make test`, and the specs drive the built command. The toolchain builds itself with the tsdown it ships to everyone else, so there is no second toolchain, only the order of two gestures.

## The command

`typescript check` runs up to fifteen passes, most of them separate processes — tsc, oxlint, oxfmt, knip, publint, dependency-cruiser and the checker program of this package's own. The command starts them all, awaits each, and reports each in one fixed order ([Quality checks](06-quality-checks.md)); a pass whose answer is this package's own code — the knip config merged, the sweep a tool is handed, oxlint's report drawn — runs in the command itself, as a function.

The rule the split follows: **the command decides whether a gate applies; the checker decides what the gate says.** Whether a `.gitignore` exists, whether a repository is a repository, which workspace members own a `specs/` — those are the command's probes. What is wrong with a `.gitignore`, or with a `docs/` tree, is a pass's, because the answer needs parsing and a rule roster.

A refusal the command's own code can meet from a project — a map it cannot compile, a tree its sweep cannot read — is thrown in four parts, `found: … · why: … · fix: … · read: …`, the read a heading of this manual; one only the toolchain can cause is `invariant()`, whose message says the bug is the toolchain's ([Testing](https://github.com/jterrazz/package-typescript/blob/main/docs/03-testing.md#who-a-rule-is-for)).

## The importable surface

The barrel and five subpaths, all declared in the exports map — each a built `.js` beside the `.d.ts` the build generates, but for the one JSON list, whose type the file itself is:

| Subpath                                    | Exports                                                                                              |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `@jterrazz/typescript`                     | the barrel — `{ oxfmt, oxlint }` presets                                                             |
| `@jterrazz/typescript/oxlint`              | the six profiles, `compose()`, `layers()`, `nested()`, `hexagonal` + `HEXAGONAL_MAP`, `defineConfig` |
| `@jterrazz/typescript/oxfmt`               | `base`, and oxfmt's own `defineConfig`                                                               |
| `@jterrazz/typescript/docs`                | `auditDocs()` — the manual's rules, pure                                                             |
| `@jterrazz/typescript/config`              | `defineConfig()` and `JterrazzConfig` — the family's settings file, typed                            |
| `@jterrazz/typescript/oxlint-config-names` | the names oxlint looks for a config under, in its order — a JSON array                               |

The oxlint entry carries the six profiles by name — `node`, `next`, `astro`, `expo`, `bun`, `react` — plus four things about composing them: `compose()` merges configs left to right, `nested()` strips the root-only options from a profile a subtree's own config ships ([Developing](02-developing.md#a-subtree-on-another-profile)), `layers()` compiles a declared layer map into `no-restricted-imports` overrides, and `hexagonal` is the map this package ships, with `HEXAGONAL_MAP` the declaration behind it. Each config TYPE — `OxlintConfig`, `OxfmtConfig` — is re-exported from the tool that owns it, never restated here: a hand copy drifts, and a drifted copy stops a consumer's own config from type-checking.

Each one re-exports the underlying tool's `defineConfig` on purpose: a consumer's config file names `@jterrazz/typescript` and nothing else, which is the one-devDependency contract holding under pnpm's strict `node_modules` ([Developing](02-developing.md)). `specs/surface/package/exports.test.ts` resolves every subpath by its public specifier and loads the built entries — the package is its own consumer #1.

`./config` types the one settings file of the whole family, `jterrazz.config.ts` ([Developing](02-developing.md)). `JterrazzConfig` is an interface so that each sibling package adds its own section by merging into it — `@jterrazz/test` declares `test` — and this entry never names a section it does not read.

`./oxlint-config-names` is the one list of the names a project's own oxlint config may take. `check` and `fix` read it to decide whether a project has a config or is handed the default, the drift report reads it to say which, and it is exported so that `@jterrazz/test`'s checker reads the same list rather than a copy of it, and counts a config exactly where this toolchain does: one owner, and a sibling that imports rather than restates.

`./docs` is the odd one out: it is not a config, it is a gate's rules, exported because that gate has two readers. `typescript check` reads a project it is installed in; an estate sweep reads clones it has installed nothing into. One pure function over a plain tree, and the rule ids, sentences and rosters stay in one executable copy.

## Two TypeScript compilers, on purpose

`typescript check` type-checks with the official TypeScript 7 Go compiler, pulled in through the per-platform `@typescript/typescript-*` optionalDependencies and resolved by path by the command.

The ordinary `typescript` dependency stays on ^6 because two consumers need the JavaScript compiler API that the Go package no longer ships: `dependency-cruiser` (a `typescript <7` peer) and `eslint-plugin-perfectionist`, which does a bare `require('typescript')`.

**Never add `typescript@7`, or an npm alias of it, to this tree.** Under pnpm's hoist fallback it can hijack perfectionist's lookup and fail intermittently with `isExternalModuleNameRelative is not a function`.

## The unit is the workspace package

Every per-package gate measures from the nearest `package.json`, never from the repository: a workspace root runs those gates once per member, and a single-package project is the one run it always was. `lint/engine/project/workspace-members.ts` answers what the members are, and every caller asks it rather than guessing.

The one gate that measures from the repository instead is the manual's, because a manual answers for a whole tree ([Quality checks](06-quality-checks.md)).
